  4. Pros and cons, tied to the code

  Pros
  - Help and CLI: bindings explain "d d" could report the row, its level, the
    request with the target filled in (the ev.Level retarget in runRow), its
    FromRow arguments, and whether a confirm will follow. Today the ? help can
    only list candidate rows, not say which one wins.
  - Tests: they could assert on the resolved request without running handlers.
    Many keytest cases would get simpler.
  - Debugging: the hardest cases are capture-pass versus bubbling and the
    innermost key class (the terminal's any) stopping the scan. An explain call
    shows the winning level directly.

  Cons and risks
  - One key isn't one event. dispatchIn has four outcomes, not one:
    - run a row;
    - wait: enterPrefix with a fallback request, and nothing executes;
    - flush: an unmatched prefix runs its fallback, then calls r.Dispatch(key)
      again;
    - unclaimed.
      On top of that, runRow itself re-dispatches the key when Binding.Replay is
      set, and leaves pending modes before and after. So Resolve has to return
      a tagged union, and Run can produce more events.
  - Side effects inside the resolve step:
    - expirePrefix() at the top of Dispatch can execute a fallback;
    - the macro-recording shadow mode is built on the fly;
    - r.rowRequest = true;
    - the Sourced("key:…") label.
  - Live state: guards inside lookup and r.argument for FromRow read live data.
    That's fine for "what would happen now", but an event saved and run later
    could be stale (a row deleted, focus moved).
  - Macros: they record keys, not events. Dot-repeat already replays requests. A
    public Run(ev) adds a third replay form that sits beside the other two
    without any rule tying them together.
  - Cost: resolve.go is the most heavily tested part of the runtime. Splitting
    dispatchIn touches every pending-mode path, and the resolver value-objects
    prototype was set aside for the same reason.

  5. Recommendation

  Do a smaller version: split internally, expose a read-only explain, and add no
  public interception.

  // resolve.go — no side effects; Dispatch == apply(resolve(...))
  type StepKind string // "run" | "wait" | "flush" | "none"
  type Step struct {
      Kind     StepKind
      Level    string   // instance id the row matched at
      Binding  *Binding // the row (Keys, Capture, Replay)
      Request  *Request // target and FromRow arguments filled in
      Fallback *Request // wait/flush: what the prefix would run
  }
  func (r *Runtime) resolveIn(focus string, mode ModeState, key MacroKey) Step
  // unexported

  // public, read-only: walks a key sequence on a copy of ModeState
  func (r *Runtime) Explain(keys string) []Step
  // operation: bindings.explain {keys, focus?}; CLI: ochazuke bindings explain 
  "d d"

  - Keep Dispatch as the only thing that runs keys.
  - Expiry and macro shadowing stay in Dispatch. Explain builds the shadow mode
    itself, without calling expirePrefix.
  - Treat item 6 (the event stream) as separate work, still waiting for znbu as
    planned.

  Tests that would pin it
  - TestDispatchEqualsResolveThenApply: for each existing keytest fixture,
    resolveIn then apply produces the same history entries, mode and focus as
    Dispatch.
  - TestExplainHasNoSideEffects: compare Mode, Focus, pending state, History(0)

  - TestExplainSequence: on a list row, d d gives a run step with row.delete

  - Explain cases for:
    - capture precedence;
    - the terminal key class ending the scan;

  - TestBindingRowsAreAtomic stays as it is.

  and that's item 1 on the same list, event bubbling. Item 6, "events out",
  points the other way: the runtime announcing what changed after it happened.
  Three ideas got blended, and only one of them is unbuilt.

  The three ideas

  1. Keys in, as events with a target. This is item 1, bubbling and capture, and
  it's already built. In the DOM, a keydown goes to the focused element and
  bubbles up through its parents. ochazuke does the same thing today:

  // resolve.go:17
  type KeyEvent struct {
          Key   MacroKey
          Mode  ModeState
          Focus string // the target: the focused instance
          Level string // the instance whose level is answering
  }

  Dispatch walks from Focus out to app (bubbling). Capture rows go first, outer
  to inner (capture phase). So the keypress-as-event-with-a-target model you're
  describing is already how keys come in.

  2. Events out. This is item 6, what the 10-24 agent proposed, and it's not
  built. "Out" means out of the runtime to anyone listening, after something has
  already happened. The DOM analogy was focusin and change: you don't send
  those, the browser tells you about them. In ochazuke these would be events
  like:

  {type: "focus", from: "row-7", to: "row-8"}
  {type: "mode",  from: "normal", to: "insert"}
  {type: "modal", opened: "confirm"}
  {type: "job",   id: 3, state: "done"}

  Listeners (logging, ochazuke subscribe, tests) watch these but can't stop or
  change anything. The history ring (item 6a) is the part that got built, and it
  records executed requests, not state changes.

  3. The resolver returns an event instead of running it. That's the Resolve/Run
  split. Nobody proposed it before 10-26. The coordinator wrote it when you
  asked, reading "event out" as the output of the key handler.

  and I don't think you want it. (I'm reading "modal" as Vim-style modes like

  The part that's right

  To isolate the mode engine (modes, prefixes like g, counts, capture,
  bubbling), it must stop executing things. Then it becomes a state machine:

  // (state, key) in → (new state, what to do) out. Nothing runs.
  next, step := keymap.Feed(state, key, env)

  - state holds the mode, the pending prefix, the count and the macro-recording
    flag.
  - step is run / wait / flush / none, plus the request, as in the doc.
  - env is read-only: the walk from the focus outward, guard answers, and the
    drawing order for spatial motions.

  That engine would be pure, testable on its own, and usable by a program that
  has nothing else from ochazuke. resolve.go already imports only the standard
  library, which is a good sign this can be done.

  The part I'd push back on

  Executing a request means ExecuteAt: the operation registry, Confirm, history,
  dot-repeat, Sourced, and the CLI and socket running the same operations.
  That's ochazuke's core, not plumbing around the resolver. If apps executed
  requests themselves:

  - every app would rebuild confirm, history and dot-repeat, or lose them;
  - a key and ochazuke task done from the CLI could start behaving differently,
    which breaks the "keys and CLI are the same operation" invariant.

  So the better split is two layers inside ochazuke:

  1. The keymap engine (new package, pure): keys in, steps out.
  2. The runtime (existing): takes a step and runs it through ExecuteAt.
     Dispatch becomes "feed the engine, then run the step."

  An app that wants full control can use only the engine and run the steps
  itself. Everyone else keeps today's behavior.

  What makes it real work

  - Mode changes are operations today. mode.enter, count.append, macro.record
    and mode.leave run through Execute like any verb (the stayingRequests list
    in resolve.go). In a pure engine they become internal state changes, so the
    engine owns mode state instead of the runtime.
  - One key can produce several steps. A flushed prefix runs its fallback and
    then replays the key. A Replay row runs, then re-dispatches. So Feed returns
    a list of steps, not one.
  - Guards and spatial motions read live data. The engine takes them as answers
    in env rather than reading the runtime, and the runtime supplies them.

  It's a real refactor of resolve.go and the mode operations, about the size of
  the value-objects prototype you set aside. It's worth doing if you want the
  mode engine reusable outside ochazuke or tested in isolation. If you only want
  "what would this key do?", the smaller internal split from the doc gets that
  for much less.

  - macro.register {text: "a"} names the register, then either starts the

  go away entirely. The engine would return "run the fallback, then feed j
  again", and the app's own loop would follow it. Either way, the engine decides
  that it happens, and the app does it.

⏺ That works, and it's a real technique: a branching preview. Wherever the
  outcome depends on a decision the preview can't see, it splits and follows
  both possibilities, and you see every way the keys could play out.

  How it would work

  The preview needs to know where to split, because any app step could change
  the mode. The bounded version has the app declare which modes an operation may
  enter, as data:

  "operations": {
    "row.delete": {"may": ["confirm"]},
    "cell.edit":  {"may": ["insert"]}
  }

  The preview then walks the keys, splitting at each step that declares
  outcomes. Each branch carries its own copy of the engine state and its own
  mode. For d d y it would show:

  d d y
  ├─ row.delete → mode confirm  (app asks)
  │   └─ y → confirm.yes → mode normal
  └─ row.delete → mode normal   (app doesn't ask)
      └─ y → wait "y"  (y y duplicates; timeout yanks)

  Both branches run on the same keys in different modes. That's the weirdness
  you mean, and it's also the whole point: you see that y means something
  completely different depending on the app's choice.

  What it adds beyond the copy

  ┌──────────────┬───────────────────────────────┬──────────────────────────┐
  │   Preview    │            Answers            │           Cost           │
  ├──────────────┼───────────────────────────────┼──────────────────────────┤
  │ Pure         │ What the keys mean if no app  │ Cheapest; wrong after    │
  │              │ step changes the mode         │ app decisions            │
  ├──────────────┼───────────────────────────────┼──────────────────────────┤
  │ Copy-and-run │ What will happen, here and    │ Runs app code on a copy; │
  │              │ now                           │  exact, one path         │
  ├──────────────┼───────────────────────────────┼──────────────────────────┤
  │ Branching    │ Everything that could happen  │ No app code; the number  │
  │              │                               │ of paths can grow        │
  └──────────────┴───────────────────────────────┴──────────────────────────┘

  The three combine well. The copy finds the real path, and the branching
  preview shows the alternatives next to it, with the real one highlighted.

  The branching one is most useful for things the others can't do:

  - Help and teaching: "in this spot, y either confirms or starts y y."
  - Checking the keymap: it can find keys whose meaning flips depending on an
    app decision, which are the places most likely to surprise a user. For
    example, it would flag the y after d d.
  - Tests: it walks every declared path without setting up app state for each
    one.

  Costs

  - The number of paths can blow up. Every splitting step doubles them. In
    practice there are few such steps, and two branches that reach the same mode
    and pending state can be merged. A cap of about 8 branches with a "+N more"
    note keeps it bounded.
  - The declarations can go stale. If row.delete starts entering a mode it
    doesn't declare, the branching preview silently misses it. A test can catch
    this by running each operation on a copy and checking that every mode it
    enters is declared.
  - Branches only cover modes. They don't show what a branch does to the data
    (which rows a delete removes). For that, combine it with the copy: the copy
    shows the data change on the real path, and the branches show the mode
    alternatives.

  My recommendation

  Build it as a third preview on top of the other two, not instead of them. The
  engine needs no changes: branching is a loop over Feed with copied states,
  plus the app's may table. Start with may on the two operations that already
  change modes, row.delete and cell.edit. Then add the check that flags keys
  whose meaning flips between branches, since that's the most useful thing a
  branching preview tells you.

⏺ What the "may table" is

  It's a small piece of data the app hands to the branching preview. For each
  operation, it lists the modes that running it might switch to:

  "row.delete": {"may": ["confirm"]}

  It exists because of the rule we settled: deciding to change the mode happens
  in app code, and the preview doesn't run app code. Without the table, the
  preview can't tell which steps might change the mode, so it has to either
  split at every step or never split. With it, the preview splits only where the
  app says a split can happen.

  A better name

  "May" is vague, and "options" is too general (the Fork type already uses
  Options). The name should say it's about modes, and it should separate two
  cases the table currently mixes:

  - Sometimes: row.delete enters confirm mode only if the app decides to ask.
    The preview splits here.
  - Always: cell.edit always enters insert mode. The preview shouldn't split; it
    should just follow the change.

  I'd use two fields on an operation entry:

  "operations": {
    "row.delete":  {"mayEnter": ["confirm"]},
    "cell.edit":   {"enters": "insert"},
    "edit.commit": {"enters": "normal"},
    "confirm.yes": {"enters": "normal"}
  }

  - enters is a certain change: no split, the preview just switches modes.
  - mayEnter is a possible change: split into "entered X" for each listed mode,
    plus "stayed".

  It reads as plain English ("row.delete may enter confirm", "cell.edit enters
  insert"), and the matching Fork field becomes Fork.Modes instead of Options.

  I'd put it on the operation, not on the keymap row, because the decision
  belongs to the operation no matter which key triggers it. d d from a key, from
  a macro, or from a palette all lead to the same row.delete, and all share one
  declaration.

  There's no separate "pure" preview. It becomes the no-split policy in the

  paths, _ := km.Explore(st, env, keys, ops, modal.NoForks, limit)

  NoForks still follows every enters, because those changes are certain. At each
  mayEnter, it takes "stayed". FollowAll takes every option, and Pick(...)
  takes the named ones.

  opened from, rather than always to normal. That needs a value meaning "the
  mode before", such as "enters": "@previous". I'd leave it out until the app
  actually opens a confirm from somewhere other than normal mode.

  │ CSV Sheet.Run │ Runtime.ExecuteAt and the handlers it calls             │
  └───────────────┴─────────────────────────────────────────────────────────┘

  So "the app decides" mostly lands in the framework, not the application.
  That's fine, since ochazuke is the app shell.

  What maps over cleanly

  - Steps out: dispatchIn becomes a pure function that returns steps, and
    Dispatch becomes "resolve, then run". Binding.Replay and the re-dispatch
    when a sequence breaks off both become Step.Replay.
  - mode.set as an event: the operations already exist. What changes is that the
    Runtime becomes the only writer. Today several places write the mode:
    setMode, SetMode, leaveMode, enterPrefix, and runRow leaving a pending mode
    before and after.
  - Atomic rows: unchanged. TestBindingRowsAreAtomic stays.
  - ochazuke bindings explain "d d": this is the branching preview with NoForks
    or FollowAll. The ? help and the pending-key hints in the footer could use
    it too.
  - The timer: stays in the host (BindingTimeoutCommand), as in o-modal.

  What it would overturn

  1. Pending conditions stop being modes. AGENTS.md says: "Every pending
     condition is an exclusive mode with a typed Payload on Runtime.Mode",
     meaning count_pending, g_pending, register_pending, "normal g", and the
     macro_recording shadow. In the o-modal design, prefix and count are engine
     memory, and Runtime.Mode holds only modes a user would recognize.
     Everything that reads pending modes would have to read engine state
     instead: the footer hints, bindings.list tables per pending mode, and
     terminal.go's leader_pending check.
  2. Dot-repeat would replay keys instead of requests. MIGRATION-PLAN.md:311
     says history.repeat "re-executes the last repeatable request", and the
     decision then was "macros stay key-based; dot is request-based". Your
     round-trip rule reverses that. Operation.Repeatable survives as the
     "repeatable" flag. The "confirmations are not re-asked" behavior then comes
     from the replayed y, not from a stored confirmed: true.
  3. Macros move out of Dispatch. Today recording is a shadow mode set up inside
     Dispatch. It would become a recorder at the entry point, Model.Update or a
     wrapper around Dispatch, which sees only typed keys.

  Where ochazuke differs from the CSV app

  - Confirm isn't just a mode. In ochazuke it opens the confirm noun's modal.
    Focus moves into the modal, and the stack walk changes (the top modal is a
    boundary). So the preview's possible outcomes are more than modes: a branch
    can also open a modal, move focus or change page. preview.possibleModes
    would have to grow into something like preview.possibleOutcomes, or a
    sibling possibleModals.
  - Confirm declarations could be automatic. Every verb with Operation.Confirm
    set opens the confirm modal, so the framework can add that preview entry
    itself. That removes the largest source of stale declarations.
  - Spatial motions and guards read the last frame (Runtime.Placed). The
    engine's input would have to carry the drawing order, and the branches would
    share the current one, which goes stale once a branch opens a modal.

  The copy-and-run preview

  This one is hard to bring over in general. Forking the Runtime is the easy
  part, because nouns, instances, focus, mode and registers are data. But
  application state lives inside handler closures (the CSV grid, list rows), and
  some handlers reach outside the process: actions.json commands, jobs, files,
  the socket. None of that can be copied.

  It would have to be opt-in:

  - An application implements a fork hook for its own state.
  - Every outside effect goes through a channel the copy can turn into "would do
    X". The v0.4.0 UI sinks already do this for notices and status, but nothing
    does it for commands, jobs or files yet.
  - Without the hook, explain uses the branching preview only. That works for
    every app, because it never runs application code.

  How I'd stage it, if you decide to

  1. Pull the pure resolver out of resolve.go, with Dispatch as "resolve, then
     run" and no behavior change. The existing keytest suite is the check.
  2. Add bindings explain on the branching preview, with automatic entries for
     verbs that confirm.
  3. Make the Runtime the only mode writer, and move pending conditions out of
     Runtime.Mode. This is where the AGENTS.md invariant gets rewritten.
  4. Switch macros and . to replayed keys. This is where the dot-repeat decision
     gets revisited.
  5. Add the opt-in fork hook and the effect channels, only if a real app needs
     exact previews.

  Steps 1 and 2 are low-risk and useful on their own. Steps 3 and 4 are where
  the real cost and the decisions are.

  Agreed, let's talk them through separately. The open part is where recording

  Side effects in previews: stub at the boundary

  That's simpler, and better. It gives one rule for both previews:

  ▎ A preview models only what changes how the next key resolves: the mode, and 
  ▎ in ochazuke the focus. Everything else is a side effect, stubbed at the 
  ▎ boundary and recorded: "called row.delete → would ask for confirmation", 
  ▎ "would run git fetch", "would write people.csv".

  So possibleModes stays, because the mode changes what y means. "Possible
  modals" and "possible outcomes" go away: they're just side effects. A test
  does the same thing at the same boundary: stub it, then assert it was called.

  A sandbox for live previews

  Yes, and it's the right step up from stubbing files. Stubbing says "would
  write people.csv". A sandbox actually writes it, to a copy, so you can see the
  result.

  - Copy on first write: the preview's file layer reads real files, but the
    first write to a path copies it into a temp directory, and every later read
    or write of that path uses the copy. At the end the preview can show a diff
    against the real files, then delete the temp directory.
  - This needs a file layer: the app has to reach files through an interface
    (open, write, rename) instead of os directly, so the preview can swap in the
    overlay.
  - External commands are the limit. git push, network calls and other processes
    can't be sandboxed this way. A command run in the temp directory can still
    touch absolute paths or the network. Those stay stubbed unless the operation
    is declared safe to run in the sandbox.

  How Haskell handles side effects

  In Haskell, a function isn't allowed to do anything. It can only compute a
  value from its inputs. So how does a program ever print or write a file?

  It returns a recipe instead of doing the thing. A function that "writes a
  file" actually returns a value that describes writing the file: a note saying
  "write this text to this path". Nothing happens when the function runs. You
  get the note back.

  The runtime is the only cook. Your program as a whole hands one big recipe to
  the Haskell runtime, and only the runtime carries it out. Everything before
  that is just building recipes.

  A monad is the "and then" glue. Recipes need to be chained: "read the file,
  and then with what you read, write a summary". The second step depends on the
  first one's result, which doesn't exist until the recipe is actually run. A
  monad is the standard way to say "do this, then pass its result to the next
  step" while still only describing the work. The do notation you see in Haskell
  code is a readable way of writing that chain.

  Why this matters for us: a recipe can be carried out more than one way.
  Advanced Haskell code uses one recipe with different interpreters:

  - the real one actually writes files;
  - a test one records "write was called with these arguments", which is your
    stub at the boundary;
  - a preview one writes into a temp directory, which is your sandbox.

  That's what we've been building:
  - Feed returning steps is "return a recipe instead of acting";
  - the app's Run is the cook;
  - the copy, the stubs and the sandbox are different interpreters of the same
    recipe.

  Bubble Tea's tea.Cmd is a small version of the same idea. Update returns a
  command describing work, and the Bubble Tea runtime is what runs it.
