⏺ Yes, it would help, and this repo is an unusually good candidate for it. Here
  is why, what I would build, and the one caveat.

  Why it pays off here

  - The package is flat. 125 Go files and about 26k lines sit in one directory
    with no subpackages, so an agent gets no navigation hints from folder names.
    It has to grep or read the 640-line README, which costs roughly 7k tokens
    before any work starts.
  - The repo has no CLAUDE.md or AGENTS.md. Every fresh agent and subagent
    rediscovers the ownership rules, the modal stack, and the palette grammar
    from scratch.
  - You already have a docgen command that emits an architecture diagram. That
    is a picture, not a lookup table. A code map is the lookup table.

  What I would build

  1. A tiny CLAUDE.md at the repo root, under 60 lines. It holds only what the
     code cannot tell you: ownership invariants, conventions, where the map
     lives, and a pointer to the references file. This file is loaded every
     session, so every line costs tokens every time. Keep it lean.
  2. A generated docs/CODEMAP.md, loaded on demand. A Go program using the
     go/ast package walks the package and emits one entry per file. This matches
     your determinism rule: regenerate with a make target, never hand-edit, so
     it cannot drift.
  3. A hand-written docs/REFERENCES.md for the Bubble Tea projects, with a
     generated header block for the facts that can rot.

  The map shape I have in mind:

  // docs/CODEMAP.md, one record per file, generated
  { file: "palette.go",
    purpose: "Nested verb/noun command palette state",   // from the file's top 
  doc comment
    exports: ["Palette", "NewPalette", "PaletteNoun"],
    keyFuncs: ["(*Palette).Update", "(*Palette).View"],
    tests: "palette_test.go",
    touches: ["bindings.go", "model.go"] }             // files that import its 
  symbols most

  Plus a short "where does X live" index at the top: modal stack, registers,
  yank history, path picker, each mapped to two or three files.

  The references section

  Only one other project under ~/proj imports Bubble Tea. I checked go.mod files
  down to four levels deep.

  ┌─────────┬───────────┬─────────┬─────────────────────────────────────────┐
  │ Project │  Bubble   │   Go    │              Existing docs              │
  │         │    Tea    │  files  │                                         │
  ├─────────┼───────────┼─────────┼─────────────────────────────────────────┤
  │ gmtm    │ v1.3.10   │ 114     │ docs/architecture.md,                   │
  │         │           │         │ tuios-protocol-notes.md                 │
  └─────────┴───────────┴─────────┴─────────────────────────────────────────┘

  So the references file would be short and should answer "which two files do I
  open" rather than describe the project:

  { project: "~/proj/gmtm",
    bubbletea: "v1.3.10",              // generated, so version bumps stay true
    readFirst: ["docs/architecture.md"],
    patterns: {
      "tuios protocol client": ["internal/..."],  // filled after I read gmtm
      "multi-window model":    ["..."] },
    sharedWith: ["ochazuke uses the same bubbletea version, no v2 migration 
  needed"] }

  If you expected more projects, they may import the v2 path
  charm.land/bubbletea/v2 or live outside ~/proj. Tell me and I will widen the
  scan.

  The caveat

  A stale map is worse than no map, because agents trust it and skip
  verification. That is why the per-file section must be generated and the
  hand-written parts must stay small and slow-changing.

  If you want it, say go and I will build all three files, add the generator as
  cmd/codemap, wire a make target, and commit.

  What changed in v2

  // v1 (what ochazuke uses today)
  Model.View()  -> string
  tea.KeyMsg    = { Type, Runes, Alt }                // one struct, no release 
  events
  tea.MouseMsg  = { Action, Button, X, Y }            // one struct

  (tea.WithAltScreen, tea.SetWindowTitle)

  // v2 (charm.land/bubbletea/v2, what your other 9 projects use)
  Model.View()  -> tea.View{ Content, Cursor, AltScreen, MouseMode, WindowTitle,
                             BackgroundColor, ForegroundColor,

  Code, Mod, Text }

    directly.

    package only uses viewport from Bubbles, so that part of the move is small.

  - Vim-style modes want a real cursor whose shape changes per mode. v1 cannot
    do that. v2 can, per frame.

    disambiguated modifiers.

    Today AGENTS.md has to warn agents not to copy v2 code in.

⏺ Yes. That is exactly what v2's View was designed for, and tuios already does
  it for terminals inside panes.

  How it works in v2

  The View you return each frame carries an optional real cursor, positioned
  relative to the top-left of the whole frame:

  tea.View{
    Content: panelsRenderedAsString,
    Cursor: {
      Position: { X: panelX + emuCursorX, Y: panelY + emuCursorY },
      Shape:    emuCursorShape,   // block, underline, bar
      Blink:    emuCursorBlink,
      Color:    nil,              // terminal default
    },
  }

  The renderer places the terminal's hardware cursor there after drawing. Your
  panel can be any size at any offset, since you just add the panel's origin to
  the emulator's reported cursor position. Set Cursor to nil and the cursor
  hides.

  What tuios does, in internal/app/cursor.go

  - Returns nil when the focused thing is not a terminal, when an overlay or
    modal covers the pane, during a resize gesture, in copy mode or scrollback,
    or when the guest program itself hid its cursor.
  - Otherwise reads the focused window's emulator for position, hidden flag, and
    style, and translates the position into frame coordinates.
  - Panels that take typing, like a search box, draw their own caret as a
    character while the terminal cursor is nil, so there is never a second
    blinking cursor behind an overlay.

  The one constraint

  A terminal has one hardware cursor. If you show several live panels at once,
  only the focused one gets the real cursor. The unfocused ones need a drawn
  block character if you want a cursor marker there at all. That is how every
  multiplexer handles it, including tuios.

  So gmtm's missing cursor is a v1 limitation plus a rendering gap, and a new v2
  app avoids it by construction. The emulator you'd use, x/vt or ultraviolet's,
  reports cursor position and visibility, so the per-frame computation is a few
  lines.

  ### 1. What tuios offers as a library and what only as a binary/daemon

  - **`pkg/tuios`** (`pkg/tuios/tuios.go`) wraps the whole window manager. `type
  Model = app.OS`, there are about 15 `With*` options, plus `New`, `NewForPTY`
  and `ProgramOptions`. It does not export panes, rendering pieces or a protocol
  client. You embed all of tuios as a Bubble Tea v2 model or nothing.
  `pkg/fuzzy` and `pkg/applist` are small helpers. All of `pkg/` is 3,476 lines.
  - **Separate modules** (AGENTS.md lines 110-141, `go.work`). They are not
  allowed to import any tuios internals:
    - `tuios.dev/vt` (26.7k lines): a terminal emulator. Its README says it is

  ### 1. Keep as-is
  - **Operation registry and its validation.** `Execute` checks arguments, then
  resolves layer actions from the innermost layer outward, then falls back to
  `op.Run` (runtime.go:232-256). It has no UI or tea dependency. This is the
  core and it ports unchanged.
  - **CLI over the registry.** `CallMsg` hands the reply to the UI loop through
  a channel (transport.go:30-44). The socket server's two goroutines are the
  only `go` statements in the package (transport.go:75,81). This already matches
  matomeru's CLI-first design and redeck's bus (`Spec`, `Call`, `List`),
  without needing their `unit.verb` naming.
  - **Modal stack and retained page frames.** `Push`/`Pop`/`OpenPage`
  (runtime.go:203-230, pages.go:50-62) carry no rendering concerns.
  - **Binding sequence engine.** Precedence, prefix handling, timeout and
  generation counter (bindings.go:94-152) stay. Its only tea type is `tea.Cmd`
  (bindings.go:56).
  - **Async pattern in Picker.** Generation IDs, a pending-command queue and
  `HandleMessage` (picker.go:405-470) are the right shape for async work.
  Generalize it rather than replace it.
  - **tea is confined.** Only model.go, bindings.go and picker*.go import tea.
  Everything else works on key strings, so the migration surface is small.

  ### 2. v2 pressure points (where a straight port leaves scar tissue)
  - **Keys as v1 `KeyMsg.String()` strings.** That string format is the shared
  key vocabulary everywhere: `Binding.Keys`, `MacroKey.Key`, the editor switches
  (editing.go:356-394), palette hjkl remapping (palette.go:483-498),
  `literalInput` (editing.go:403-423) and paste encoded as `"[...]"`
  (editing.go:333, macros.go:72).

  `literalInput` rejects anything with a `shift+` prefix, so those letters would
  stop inserting.
    - v2 delivers paste as its own `PasteMsg`, which breaks the `"[...]"`
  encoding.
    - The rune-splitting hack (model.go:95-109) becomes dead code.
    - **Seam:** one key-normalization function, so the rest of the code keeps
  its strings: `{name: "ctrl+a", text: "", paste: false, raw: <tea.Key>}`.
  Binding names stay stable and text insertion uses `.text`. A terminal pane
  needs `raw` to re-encode keys for the PTY; a string cannot round-trip that.
  - **Fake cursor.** `InputView` writes raw `\x1b[7m` (model.go:414-418) and
  mixes cursor painting with selection painting. v2's real cursor needs absolute
  X/Y, but layout is coordinate-blind string concatenation:
  `Layout.Page/Panel/Split/Sidebar` (layout.go:46-147) and `ComposeModal`'s
  computed left/top (surface.go:69). Porting as-is means keeping the fake cursor
  forever and losing a bar cursor for insert mode.
    - **Seam:** a small cursor-carrying render result such as `Block{Text,
  Cursor *Pos}`. Each composer (Panel, Split, Sidebar, ComposeModal, Model.View)
  offsets the cursor position. Only the innermost focused component claims the
  cursor.

  patches with a forced `\x1b[0m` and wraps the backdrop in Muted

  replace this and could dim the backdrop correctly.

  internals and keep string bodies.
  - **Theme.** `lipgloss.AdaptiveColor` (theme.go:80) is gone in v2. It needs
  `BackgroundColorMsg` plus a light/dark choice held in `Appearance`.

  1. Is ochazuke the right move for the znbu app?

  Yes on direction, with two warnings. The znbu docs demand exactly what
  ochazuke is building: a registry that owns pages, actions, palette entries,
  modals and forms, one input engine with separate normal and input binding
  maps, Vim-like normal mode, Readline on every single-line input, a nested
  verb/noun palette, one modal slot plus a parked modal, and a CLI generated
  from the same registry. The docs explicitly reject Huh for forms. None of that
  exists in tuios, and both prior attempts had it only on paper.

  The post-mortem on gmtm and matomeru is blunt. Bubble Tea was not the cause.
  Both had registries, but the shell still hand-dispatched by page name, form ID
  and action string:

  // matomeru internal/ui: 71 checks like this, actions.go alone is 1726 lines
  if (m.page == "panes" && key == m.binding("panes", "fold")) { ... }

  // gmtm exec.go: 30-case string switch over action IDs inside the "thin" 
  orchestrator
  switch (actionID) { case "pane-project": ... case "context-save": ... }

  The registry described things. It did not own dispatch. Ochazuke's "register
  an operation, not a key case" rule is the right fix, and runtime.go's layered
  resolution already does it with no UI dependency.

  The two warnings:

  - Scope and pace. matomeru grew to 75 forms and a backlog of Slack, GitHub,
    Linear and MCP in five days with zero unit tests. Ochazuke has the same
    commit rate and a docs folder that is mostly HTML plans. The failure mode
    was speed without a settled interaction model, not the library.
  - A framework without a consumer is the opposite over-scope. The test that
    matters is adding a second real page or app without touching model.go or
    runtime.go. Do that before adding more framework.

  Also: znbu's shipped code and its own "lessons from tuios" section are written

❯ what is huh for forms                                                         

⏺ Huh is Charm's forms library. It gives you a declarative way to build terminal
  forms and prompts: you describe fields and get a working interactive form,
  either run standalone or embedded in a Bubble Tea app as a model.

  huh.NewForm(
    huh.NewGroup(                       // a group is one screen or page
      huh.NewInput().Title("Name").Value(&name).Validate(nonEmpty),
      huh.NewSelect().Title("Shell").Options("zsh", "fish").Value(&shell),
      huh.NewMultiSelect().Title("Tags").Options(...).Value(&tags),
      huh.NewConfirm().Title("Create?").Value(&ok),
    ),
    huh.NewGroup(huh.NewText().Title("Notes").Value(&notes)),
  )

  Field kinds are Input, Text, Select, MultiSelect, Confirm, Note and
  FilePicker. It handles focus order, validation, theming, an accessible mode
  for screen readers, and dynamic fields whose options depend on earlier
  answers. It is what gum uses under the hood for its prompts.

  Why znbu rejects it. The research note in znbu lists the reasons, and they are
  about the interaction model rather than quality:

  - Huh has no normal mode and no jump-to-field. Znbu wants Vim-like navigation
    across fields with single-letter codes.
  - Each field kind ships its own keymap. That breaks global remapping and the
    help screen that derives from effective bindings.
  - Its Select cannot hold free text, so create-on-no-match is impossible.
  - Parent and child field linkage with async sources would cost more to wrap
    than to write.
  - Huh being on v2 removes only the version objection, not these.

  So Huh is the right answer for a setup wizard or a CLI prompt. For znbu, forms
  are registry data rendered through the same input engine and binding system
  as everything else, which is why ochazuke's plan is to generate forms from
  operation parameter schemas instead.

  How it maps to what you described

  ┌──────────────────────────────────┬─────────────┬────────────────────────┐
  │             Ochazuke             │    Emacs    │          Vim           │
  ├──────────────────────────────────┼─────────────┼────────────────────────┤
  │ major, one per scope             │ major mode  │ the buffer type        │
  ├──────────────────────────────────┼─────────────┼────────────────────────┤
  │ minors, stackable and toggleable │ minor modes │ plugins and options    │
  ├──────────────────────────────────┼─────────────┼────────────────────────┤
  │ state                            │ none        │ normal, insert, visual │
  ├──────────────────────────────────┼─────────────┼────────────────────────┤
  │ ancestors' modes, page then app  │ global map  │ none                   │
  └──────────────────────────────────┴─────────────┴────────────────────────┘

  Resolution is one walk. Most recently enabled minor first, then the focused
  scope's major, then each ancestor's modes out to app. Inside every mode, the
  binding variant for the current state is checked before the any-state variant,
  then the mode's grammar hook. That is Emacs precedence with Vim's state
  filter inside each map, and it is also today's inner-over-outer and
  mode-specific-over-mode-less rule, stated once instead of across four routers.

  Everything bespoke becomes a mode. ReadlineOnly is a minor called insert-only
  whose grammar swallows Escape. The Readline switch is a minor enabled by
  default on every editor, so your preference holds and other people override
  keys the same way they override anything else. The Vim switch is the editor
  major's grammar. The palette is a major on a modal scope. Escape closing a
  modal is a binding on the modal major. Macro recording is a minor pushed while
  recording. A terminal pane is a major with passthrough grammar and a
  leader-pending minor. Help becomes a mode line, which is how a user already
  thinks about it:

  app › panes › editor(insert) +readline +path-field

  What goes away. Layer, Frame.State, Input.Mode, InputPaths, validateContext
  and validateSelection. What stays untouched is the registry, Execute, the
  Binding shape, the sequence engine, the editor, lists, picker, registers,
  macros and the CLI.

  Most-recently-enabled wins is predictable, but two minors claiming the same
  key need either an explicit order or a conflict check at enable time. The
  sandbox already has that duplicate-key check, so it can be reused.

  includes the mode.

  Today's first router, as mode tables

  modes = {
    normal: {
      "q":        set.mode("macro_pending"),
      "@":        set.mode("macro_replay_pending"),
      digit:      count.append,                    // class match
      "d":        set.mode("operator_pending", { op: "delete" }),
      "g":        set.mode("g_pending"),           // yes, even multi-key 
  sequences
      ...
    },
    macro_pending: {
      alpha:      macro.start({ register: key }),  // → mode "macro_recording"
      "ctrl+c":   set.mode("normal"),
      any:        set.mode("normal"),              // unknown key cancels
    },
    macro_recording: {                             // see the overlay note below
      "q":        macro.stop,                      // → mode "normal"
    },
    operator_pending: {
      "w": motion.apply("word"), "$": motion.apply("line-end"), "d": line.apply,
      esc: set.mode("normal"), any: set.mode("normal"),
    },
    g_pending: {
      "g": move("first-line"), "G": ..., any: set.mode("normal"),
    },
  }

  dispatch(key) = (modes[state.mode][key] ?? modes[state.mode][classOf(key)] ??
  modes[state.mode].any)(key, state)

  Every conditional in dispatchKey became a row. Even the sequence register is
  gone: g g is the g binding inside g_pending, and the 400ms ambiguity timeout
  is just a timer command that fires set.mode("normal") with the fallback
  action. The state that handlers need, like which operator or register or the
  count so far, rides along as a payload on the mode.

  Key classes are a predicate language on the left-hand side, resolved exact
  first, then class, then any:

  "q"                      // exact
  digit, alpha, printable  // named classes
  not("q")                 // complement
  anyOf("h","j","k","l")
  alpha.without("q")       // your example

  The one thing that is not a plain mode: recording. In macro_recording keys
  must still do what they do, and also be appended. If recording replaced the
  keymap, j would stop moving. So recording is an overlay mode: it observes the
  key, appends it, then lets the resolution continue into the underlying mode.
  That is the Emacs minor mode again, and the one distinction the design needs
  to keep:

  exclusive mode:  replaces the keymap           // normal, insert, 
  operator_pending, macro_pending
  overlay mode:    sees every key, then passes it // macro_recording, 
  leader_pending for the terminal pane

  With that split, the whole key path is a mode stack, a lookup, and handlers
  that mutate state or run operations. No if chain, and list.bindings prints the
  real tables for whatever mode you are in, including operator_pending, which
  no help screen shows today.

❯ i love the shadow mode idea.  do you think this is a better design?           

⏺ Yes, and by a clear margin over what phase 5 of the plan says today.

  What the plan has. Nouns with bindings per state, plus a grammar hook per noun
  for the parts that did not fit in a table: the editor's counts, operators and
  pending motions, the palette's search, the terminal's passthrough, macro
  recording. The hook is an escape hatch. Anything behind it is Go code the
  resolver cannot see, cannot list in help, and cannot rebind.

  What the shadow design does. It removes the escape hatch. Every pending
  condition is a mode with a payload, every key goes through lookup(mode, key)
  with exact, class, any precedence, and handlers only mutate state or run
  operations. There is no second kind of thing.

  // the entire resolver
  stack(focus).forEach(inst =>
    table = nouns[inst.noun].bindings[state.mode.name]
    hit   = table[key] ?? table[classOf(key)] ?? table.any
    if (hit) return hit(key, state, inst))

  Nouns and modes compose cleanly: the stack says whose tables to consult, the
  mode says which table. operator_pending on an editor instance and
  leader_pending on a terminal instance are just rows.

  Why it is better, concretely

  - list.bindings and help become complete for the first time. Today they omit
    everything in the Go switches.
  - A user can rebind inside operator_pending or macro_pending, which no
    Vim-style TUI I know of lets you do from config.
  - Testing becomes table-driven: a mode, a key, an expected next mode and
    action. The eleven phase 0 goldens turn into rows.
  - Adding the terminal pane, or znbu's : command input, adds tables, not
    routers.

  Where to be careful

  - The payload needs a shape: register, count, operator, shadow. Keep it one
    small struct, not a map, so the mode machine stays inspectable.
  - Vim's compound commands like "a3dw are a chain of modes passing payload
    along. That is fine, Vim itself is that state machine, but the tables for
    the editor noun will be the largest in the system. Generate them from a
    compact spec rather than hand-writing rows.
  - Ambiguity timeouts become timer commands that fire a mode change. The
    generation guard the sequence engine already has carries over unchanged.

  What I would change in the plan. Phase 5's "stack walk with grammar hooks"
  becomes "stack walk over mode tables, no hooks", with modes carrying payload
  and shadow. Phase 0's goldens still apply. Phases 1 to 4 are unaffected. Since
  this fork is talk only, that amendment belongs in the original session before

❯ what would defining a binding look like?  in code and in a config             

⏺ Two forms, same data. A binding is a row: a noun, a mode, a key pattern, and
  what to do. "What to do" is an operation request, which is already data, or a
  mode transition, which is just the set.mode operation with a payload. Go-only
  handlers exist for the handful of rows that need to re-dispatch, like the
  recording shadow.

  In code, declaring a noun's tables

  editor := r.Noun("editor")

  editor.Mode("normal").
      Bind("i",    Do("set.mode", Args{"mode": "insert"})).
      Bind("d",    Enter("operator_pending", Payload{"op": "delete"})).
      Bind("g",    Enter("g_pending")).
      Bind(Digit,  Do("count.append")).            // class pattern; the key is 
  passed to the handler
      Bind("q",    Enter("macro_pending"))

  editor.Mode("operator_pending").
      Bind("w",    Do("motion.apply", Args{"motion": "word"})).
      Bind("d",    Do("line.apply")).
      Bind(Any,    Enter("normal"))                 // unknown key cancels

  editor.Mode("macro_pending").
      Bind(Alpha,  Do("macro.start", FromKey("register"))).   // "a" → 
  {register: "a"}
      Bind(Any,    Enter("normal"))

  editor.Mode("macro_recording").
      Bind("q",    Do("macro.stop")).When(ShadowIs("normal")).
      Bind(Any,    Func(func(k Key, s *State) error {         // Go-only row: 
  needs re-dispatch
          s.Macro.Append(k)
          return r.Dispatch(k, s.WithMode(s.Mode.Shadow))
      }))

  editor.Mode("insert").
      Bind("esc",     Do("set.mode", Args{"mode": "normal"})).
      Bind("ctrl+w",  Do("kill.input", Args{"motion": "word-backward"})).
      Bind(Printable, Do("insert.input", FromKey("text")))

  Patterns: an exact key name, a class (Digit, Alpha, Printable, Any), a class
  minus keys (Alpha.Without("q")), or a set (OneOf("h","j","k","l")). Resolution
  is exact, then class, then Any. Multi-key sequences are sugar: Bind("g g", 
  ...) expands to the g_pending row above.

  In config, overriding or adding rows

  Same shape as today's set.binding, plus pattern and payload:

  [
    { "noun": "editor",   "mode": "normal",           "keys": "U",
      "request": { "verb": "undo", "noun": "input", "args": { "steps": 3 } } },

    { "noun": "editor",   "mode": "operator_pending", "keys": "e",
      "request": { "verb": "motion.apply", "args": { "motion": "word-end" } } },

    { "noun": "editor",   "mode": "normal",           "keys": "g g",
      "request": { "verb": "move", "noun": "input", "args": { "motion":
  "first-line" } } },

    { "noun": "worktree", "mode": "normal",           "keys": "x",
      "request": { "verb": "remove", "noun": "worktree" } },

    { "noun": "terminal", "mode": "leader_pending",   "pattern": "{any}",
      "request": { "verb": "forward", "noun": "terminal", "args": {
  "withPrefix": true } } },

    { "noun": "editor",   "mode": "macro_pending",    "pattern": "{alpha -q}",
      "request": { "verb": "start", "noun": "macro", "argsFromKey": "register" }
  }
  ]

  Rules for the config form:

  - Everything a user can write is data. Func rows are not expressible in
    config, and there should be very few of them.
  - A row with the same noun, mode and pattern replaces the default. A row with
    a new pattern adds. null as the request unbinds, which is how someone who
    disagrees with you removes a Readline key.
  - list.bindings prints exactly this format for the current stack and mode, so
    the round trip is: look, copy, edit, apply.
  - The CLI path is the same operation: ochazuke binding set --json '<row>', and
    the keybinding sandbox tests a file of these rows.

  The resolver never learns a new concept for any of this. It reads
  nouns[noun].bindings[mode] and matches.

❯ what confuses me is the first know calls remove on a worktree....how does it

⏺ It knows because the target is captured as data at the moment you press the
  key, and carried along explicitly. Nothing later asks "what is focused now".

  // 1. focus is on a row; the key resolves through that row's noun
  focus = { id: "wt-main", noun: "worktree" }
  press "x"  →  worktree.normal["x"]  →  Request{ verb: "remove", noun:
  "worktree", target: "wt-main" }

  // 2. the verb has Confirm, so the framework opens a confirm instance holding 
  that exact request
  modal = { id: "confirm#1", noun: "confirm", parent: "wt-main",
            payload: { prompt: "Remove worktree wt-main?",
                       request: { verb: "remove", noun: "worktree", target:
  "wt-main", args: { confirmed: true } } } }

  // 3. y runs the stored request, not "remove whatever is focused"
  press "y"  →  Run(payload.request)  →  RemoveWorktree(ctx{ Instance: wt-main
  }, args)

  Three things make this safe:

  - The target is frozen in the request. target: "wt-main" was written when x
    was pressed. Even if focus could move while the modal is open (it cannot,
    the modal is the focus), y would still remove wt-main.
  - The handler gets the instance, never a guess. ctx.Instance.ID is the id from
    the request. The handler does not read the list's selection.
  - Whether it should be removed is the handler's job. Is it the main worktree,
    is it dirty, does it have an agent attached. That is domain logic in
    app.RemoveWorktree, and it refuses by returning a failed result with a
    message. The framework only guarantees that the handler is asked about the
    right worktree, with the user having confirmed that specific one.

  The thing the framework deliberately does not do is let a binding run against
  an implicit "current" object. Every request that reaches a handler names its
  target, and the CLI form ochazuke worktree remove --target wt-main is the same
  request with the same guarantee.

⏺ Two states, one owner, and the owner is your app.

  // your real app owns everything, including the framework runtime
  App = {
    store:    sqlite,                 // domain state: projects, tasks, 
  worktrees
    daemon:   tuiosClient,
    projects: [...],
    ui:       ochazuke.Runtime,       // interaction state: nouns, instances, 
  focus, modals, pending keys, undo, registers
  }

  The framework's app node is not your app. It is just the root of the instance
  tree, the outermost place bindings can live. Your App struct is the Go object
  that holds the runtime as a field and whose methods are the handlers.

  What each side stores

  ┌───────────────────────────────────┬─────────────────────────────────────┐
  │           Your app owns           │           Framework owns            │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │ Domain objects and persistence    │ Which instance is focused, which    │
  │                                   │ page, open modals                   │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │ Daemon connections, streams       │ Mode and payload per instance,      │
  │                                   │ pending sequences                   │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │ Business rules (can this worktree │ Editor text, undo trees, registers, │
  │  be removed)                      │  macros                             │
  ├───────────────────────────────────┼─────────────────────────────────────┤
  │ Which rows exist and what they    │ Selection and scroll within a list  │
  │ are called                        │                                     │
  └───────────────────────────────────┴─────────────────────────────────────┘

  Instances carry only an id, a noun, a label and a small interaction payload.
  Never a domain object. The id is the bridge: wt-main means something to your
  store and nothing to the framework.

  How the two meet: handlers and refresh, one direction each

  // user → domain: a handler is your method, closed over your App
  define("worktree", { verbs: { remove: app.removeWorktree } })

  app.removeWorktree = ({ instance, args }) => {
    if (!app.store.canRemove(instance.id)) return fail("dirty worktree")
    app.store.remove(instance.id)                  // domain changes
    app.refreshSidebar()                           // then the UI is told
  }

  // domain → UI: you push rows, the framework keeps selection by id
  app.refreshSidebar = () =>
    app.ui.list("sidebar").setItems(app.store.worktrees().map(w => ({ id: w.id,
  noun: "worktree", label: w.name })))

  // startup
  app.ui = ochazuke.New()
  app.declareNouns(); app.buildPages(); app.refreshSidebar()
  ochazuke.Run(app.ui)                              // the framework owns the 
  Tea loop

  No two-way binding and no shared mutable state. Domain changes become setItems
  calls. User actions become handler calls with the instance id. That is also
  what the znbu contract asks for: units own data and rules, the UI owns
  selection, scroll and modals.

  The one place they touch

  Application verbs do I/O, so they run off the loop and report back through the
  phase 6 delivery contract. Your handler returns pending with a generation,
  does its work, and the result comes back to the loop where refreshSidebar
  runs. The framework guarantees the result is matched to the instance that
  asked and dropped if that instance has since closed.

⏺ No problem. A custom grid is what the component contract exists for: it lives
  in your app or a side package, implements the same delivery interface as the
  picker, creates one instance for the focused cell, and the core never learns
  it exists. If the grid needs something the core does not provide, that is the

  Three visual modes is right. Excel has the same three, cell range, rows,
  columns, and anything else turns out to be a verb, not a mode. Select-all is a
  verb. A single cell is just normal mode. So:

  // selection is payload on the mode; motions move the cursor, the shape 
  decides what is selected
  state.mode = { name: "visual-block", anchor: { row: 2, col: 1 }, cursor: {
  row: 4, col: 3 } }

  selected(mode) = {
    "visual-block":  cells from anchor to cursor, rectangular          // v
    "visual-row":    whole rows   anchor.row .. cursor.row             // V
    "visual-column": whole columns anchor.col .. cursor.col            // ctrl+v
  }

  The tables, which are mostly shared:

  define("cell", {
    bindings: {
      normal: { v: enter("visual-block"), V: enter("visual-row"), "ctrl+v":
  enter("visual-column") },
      ...
    },
  })

  visualCommon = {
    h: "grid.left", j: "grid.down", k: "grid.up", l: "grid.right", "0":
  "grid.rowStart", "$": "grid.rowEnd",
    "g g": "grid.top", G: "grid.bottom", o: "selection.swapAnchor",
    v: enter("visual-block"), V: enter("visual-row"), "ctrl+v":
  enter("visual-column"),   // switch shape, keep anchor

  selection.yank gets the resolved cell set, and the register stores it with its

⏺ Yes, and nothing extra is needed for it. A verb does not need a binding to
  exist. The registry is the catalog, bindings are shortcuts into it, and the
  palette is the full index.

  How the palette knows what to show: it is a modal instance parented at the
  focus, so its stack still runs through the cell, the row, the column, the grid
  and the sheet. Noun-first shows the focused noun's verbs, then the ancestors'
  verbs. Verb-first shows every noun that has that verb. Searching across all
  of it is the palette's default.

  define("column", {
    verbs: {
      trim:        app.trim,                                     // no binding, 
  palette and CLI only
      upper:       app.upper,
      lower:       app.lower,
      dedupe:      app.dedupe,
      fillDown:    app.fillDown,
      split:       { run: app.split,   params: { on: { type: "string" } } },
      replace:     { run: app.replace, params: { find: { type: "string" }, with:
  { type: "string" } } },
      toDate:      { run: app.toDate,  params: { format: { type: "string", enum:
  ["iso", "us", "eu"] } } },
      sort:        app.sortBy,
    },
    bindings: { normal: { s: "sort" } },                         // the one that
  earned a key
  })

  Every verb there appears in the palette under column, gets its arguments
  prompted from params with pick lists where there is an enum, and is callable
  as csv column trim --target c2. A user who wants a key for trim adds one
  config row.

  For a catalog that is genuinely large, two refinements, both data:

  - Tags on verbs so the palette can group: { run, tags: ["text"] }. Search
    still spans everything.
  - One verb with a sourced parameter for transformations that are themselves
    data, such as user scripts or a plugin directory: transform: { params: { 
    name: { source: "list.transforms" } } }. The catalog can grow at runtime
    without a define change.

  Built-in transformations should be real verbs, since they get typed
  parameters, confirmation and help for free. The sourced-parameter form is for
  the open-ended tail.

  The same goes for the selection: selection.sort, selection.fill and friends
  are verbs on whatever noun owns the visual modes, bound or not, and the
  palette opened from visual mode shows them first because that is the focused
  noun.

❯ while transformations will probably take a whole cell as input (coming from   
  state...) each transformation might only need the cell's value.               
  well...that's jsut for text tranformations....if we get into cell math and    
  stuff.....then it will need to be able to grab values from any cell           

⏺ That distinction belongs in your app, not the framework, and it falls out
  cleanly because handlers are your methods closed over your state. The
  framework hands a handler the target instance and the arguments. What the
  handler reads is up to it.

  Two tiers of transformation, one calling convention:

  // tier 1: text transforms are pure functions on a value; the app lifts them 
  over the target
  text = { trim: v => v.trim(), upper: v => v.toUpperCase(), ... }
  app.liftText = fn => ({ instance, selection }) =>
    app.apply(cellsOf(instance, selection).map(c => ({ at: c, after:
  fn(app.get(c)) })))

  // tier 2: sheet transforms see the whole sheet and produce the same patch
  app.formula = ({ instance, args }) =>
    app.apply([{ at: instance.id, after: evaluate(args.expr, app.sheetView())
  }])   // evaluate reads any cell: sum(B2:B9), A1*2

  // both end here: one patch shape, which is also the undo record
  patch = { cells: [{ at: "r3:c2", before: "x", after: "X" }], dirty: true }

  So trim never sees the sheet and cannot accidentally depend on it, while
  formula, fillDown or a cross-column derive get a read view of everything and
  still return the same patch. Undo, redo, the dirty flag and the grid refresh
  all work on patches, so adding a tier adds no new plumbing.

  When you get to formulas, the only design question is the cell reference
  syntax in args.expr. Instance ids like r3:c2 are fine internally, and the
  evaluator can accept A1 style on top if you want it to feel like a
  spreadsheet. The framework is indifferent either way.

    trim:   v => v.trim(),
    upper:  v => v.toUpperCase(),
    lower:  v => v.toLowerCase(),
    title:  v => v.replace(/\b\w/g, c => c.toUpperCase()),

    ...                                            // grows without touching 
  nouns or bindings
  }

  // one verb, available on cell, column, row and selection
  transform: { run: app.transform, params: { name: { type: "string", source:
  "list.transformations" } } }

  // bindings are the verb with the argument filled in
  bindings: { normal: { "t u": do("transform", { name: "upper" }), "t l":
  do("transform", { name: "lower" }) } }

  // the handler is the same for one cell or many
  app.transform = ({ instance, selection, args }) =>
    app.apply(cellsOf(instance, selection).map(c => ({ at: c, after:

  Sheet-level transforms that need other cells live in a second map with the
  signature (sheet, cell) => value, and the same verb dispatches by which map
  holds the name.

  Non-adjacent selection is a marks set on the selection payload, and it does
  beat Excel, whose multi-select is awkward and breaks on most operations:

  state.mode = { name: "visual-block", anchor, cursor, marks: new Set(["r2:c1",
  "r9:c4"]) }

  visualCommon += {
    m: "selection.toggleMark",        // add or remove the cell, row or column 
  under the cursor, by the current shape
    M: "selection.clearMarks",
    "ctrl+a": "selection.all",
  }

  cellsOf(selection) = union(rangeFor(shape, anchor, cursor), marks)

  Every verb already takes a cell set, so marks cost nothing downstream: t u
  uppercases the rectangle plus every marked cell, yank stores the set with its
  shape, delete and fill do the same. Marks survive a shape switch and a cursor
  move, which is what makes it useful: mark three stray cells, then drag a
  range, then apply once.

  One rule to keep it predictable: marks belong to the visual mode's payload, so
  esc drops them. If you want sticky marks across modes later, they move to app
  state and get a visible indicator, but start with the simple version.

⏺ Methods, yes. In Go the capital letter is the visibility rule: a capitalized
  name is exported, meaning public to other packages, and a lowercase name is
  unexported, private to the package. There is no public or private keyword.

  What the agent wrote, from the working tree:

  func (r *Runtime) Define(name string) *NounBuilder        // exported method 
  on Runtime
  type NounBuilder struct { ... }                            // exported type, 
  so your app can hold one
  type ModeBuilder struct { ... }
  func (r *Runtime) DefineMode(name string, pending bool) error   // registers a
  mode, pending = it is a transient like operator_pending
  func (r *Runtime) DefineGuard(name string, fn Guard)             // registers 
  a named condition like ShadowIs("normal")

  So from your app it reads as the JS sketch did, just with Go's chaining:

  r.Define("worktree").
      Verb("remove", app.RemoveWorktree).Confirm("Remove {{id}}?").
      Mode("normal").Bind("x", Do("remove"))

  r.guards on the last line is lowercase, so that map is internal to the
  package. You reach it only through DefineGuard. That split is the Go
  convention: exported methods are the API, lowercase fields are the
  implementation.

❯ ok...go fucked up tho...public should be lowercase                            

⏺ Plenty of people agree with you. The usual defense is that it makes visibility
  visible at every call site without an import-time lookup, but the cost is
  that the public API shouts and the internals whisper, which is backwards from
  how most languages read. It also means a JSON field has to be capitalized to
  be serialized, which is why every struct carries those json:"name" tags.

  For this project it only matters at the boundary: anything your CSV app calls,
  Define, Verb, Bind, Do, has to be capitalized, and anything the framework
  keeps to itself stays lowercase. The JS-shaped sketches stay the way you think
  about it. The capitals are just Go's spelling of the same thing.

❯ is golang oss?  and please explain "are the rent" never heard that before     

⏺ Yes. Go is open source under a BSD-style license, with the source at
  go.googlesource.com and a mirror on GitHub under golang/go. Google funds most
  of the core team and steers the language, but anyone can read it, fork it, and
  contribute through the public review process. A fork that flipped the
  visibility rule is legally and technically possible. It would just be alone:
  every existing package, including Bubble Tea, assumes capitals mean exported,
  so your fork could not use any of them without rewriting their APIs.

  "The capitals are the rent" was my own phrasing, not an idiom you missed. The
  idea was: you don't own Go's ecosystem, you are using it, and the price of
  using it is accepting its rules. Capitalized exports are the fee you pay for
  Bubble Tea, the race detector, and the rest. Writing your own language means
  buying the building instead, and the building is the twenty years of
  libraries, not the compiler.

❯ still worth it to try...imagine...if go had a nicer visiblity                 
  convention...ppl would be happier to adopt it...it could gain momentu         

⏺ It is tryable, and cheaper than it sounds if you do it as a dialect rather
  than a fork. The pattern is TypeScript over JavaScript: your source has the
  rule you want, it transpiles to plain Go, and the whole ecosystem stays
  reachable.

  // yours                                  // emitted Go
  pub fn define(name string) *NounBuilder   func Define(name string) 
  *NounBuilder
  fn stack(focus string) []level            func stack(focus string) []level
  pub struct Noun { pub name string }       type Noun struct { Name string 
  `json:"name"` }

  Calls into existing packages keep their capitals, since those are someone
  else's names, and the transpiler leaves them alone. Your own code gets pub and
  lowercase everywhere, and go build, the race detector, gopls and Bubble Tea
  all keep working because what they see is Go.

  Precedents: Go+ (goplus) and Borgo are both dialects that compile to Go, and
  TypeScript is the proof that a dialect can outgrow its host when it fixes the
  thing people actually complain about. Go's visibility rule is near the top of
  that list.

  Where it gets hard is the second step, the one the toolchain does not do for
  you: error messages, debugger line mapping and gopls pointing at the dialect
  source instead of the emitted Go. TypeScript spent years on source maps for
  exactly that reason. The first step, though, is a parser, a rename pass and go
  build, which is a weekend. If you ever want to spend one on it, the ochazuke
  CSV app would be a fine first program to write in it.
