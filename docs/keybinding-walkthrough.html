00Key terms: Frames, layers, and Context

If Frames and layers feel like the same thing, they are not. A Frame is one entry in a stack that is drawn bottom to top and supplies the current key-routing Context. A layer (scope) is a named bundle of bindings and actions, looked up by ID. A Context's Path lists layer IDs. Frames do not have a numeric z-index, pixels, or a renderer. Only app is a required root; names such as playground or agent come from the demo. Source: runtime.go, model.go, pages.go, input.go, demo.go.

Two different orderings

Frames · draw + input stack

  1. Frames[2] "confirm" ← top: current Context
  2. Frames[1] "draft" (modal)
  3. Frames[0] "page" (base, drawn first)

Model.View draws the active page, then Frames[1:] bottom → top. Ordinary keys use the last frame's Context.

Context.Path · scope precedence

  1. "field" ← innermost, searched first
  2. "screen"
  3. "app" ← required root, searched last

Path is stored outer → inner (["app","screen","field"]). EffectiveBindings overlays the scopes; action handlers are searched inner → outer. This is not a visual stack.

All names above are hypothetical. In the real demo the path also contains an agent scope (["app","playground","agent","notes"]). That is a demo-only intermediate scope shared by the notes and directory inputs, not an AI agent and not a framework special case.

What a Frame holds

A Frame is { id, context, state }. It does not hold a renderer, pixel geometry, or a z-index. Its position in the Frames slice is its stacking order. state holds frame-local values such as scroll position, not all application or editor state. Text, cursor, mode, and history live on the Input, which the Frame's Context refers to by inputId.

Three relationship graphs—not one family tree

Read an arrow as the label on that arrow, not “is a kind of.” Model holds a Runtime pointer; a Page holds a Frame pointer. Neither is an inheritance relationship. “Registry” is a name for an ID-keyed map, not another object above Runtime. “Modal” is the role of a Frame above the base frame, not a separate core type.

1. Storage: who holds what?

Start at Model and follow its Runtime pointer. Runtime keeps several collections side by side—not nested inside one another. This is a selected field map, not every field in either struct. A registered Page retains its own base Frame, even when inactive.

For example, Runtime.Inputs["title"] looks up an Input. That map is the input registry. There is no separate Registry instance between Runtime and Input.

2. Active stack: which page and modals are open?

Hypothetical snapshot: the editor page has draft and confirm modals open. Settings is registered but inactive. The editor Page and Frames[0] point to the same Frame object, not copies. The modals are siblings in the Frames slice; confirm is not stored inside draft.

Pop removes confirm, making draft current. It does not rebuild draft. OpenPage can switch to settings only after both modals close; it then uses settings' existing Frame as the single base frame.

3. Context: how does a frame select scopes and an editor?

Hypothetical context: { path: ["app", "screen", "field"], inputId: "title" }. The path names Layer entries; the input ID names an Input entry. These are two separate lookups, not another stack of windows.

Ordinary key routing starts with this top-frame Context. An explicitly targeted operation can use another context. If no contextual action handles a request, execution falls back to the registered Operation's default handler.

Illustrative objects with hypothetical names. Who owns what changes: focus edits the top frame's Context; push adds a frame; pop removes it and the parent's own Context returns unchanged.

Page switching is different again: OpenPage replaces Frames with the new page's retained base frame, and is refused while a modal is open. Current keys use the last frame's context, but ExecuteAt or a Target can name another context, so not every operation is top-only. Real traces: Tab (focus) and Ctrl-N (push).

Glossary

Terms are grouped. Each term has a stable anchor (for example #term-frame, #term-layer) that the other docs link to.

Runtime objects

Runtime
The framework core, owned by one event loop. Holds Frames, Layers, Inputs, Pages, Operations, and the pending key sequence. runtime.go.
Model
The Bubble Tea adapter around a Runtime: Update receives keys and View draws. model.go.
Page
A top-level screen. It retains its base Frame and a render callback. OpenPage swaps Frames to that frame. pages.go.
Frame

One { id, context, state } entry in Runtime.Frames. The slice order is both draw order (bottom → top) and input routing: the last frame's Context is the current one. It holds no renderer, pixels, geometry, or numeric z-index.

Modal
A Frame pushed above the page by Push (the built-in modal.push operation). While one is open, OpenPage is blocked. modal.pop removes the top one. See Flow 2.
Registry
A lookup map keyed by ID: Layers, Inputs, Pages, Operations. A registry says what exists. It does not order anything.

Scope and focus

Layer / scope

A named scope { id, noun, bindings, actions } stored in the Runtime.Layers registry. It is not a visual layer and has no z-order. A layer only matters when a Context's Path names it.

Context
Where input goes: { path, inputId }. Each Frame carries one. Runtime.Context() returns the top frame's.
Path
Ordered layer IDs, outer → inner, always rooted at app. Set explicitly when a frame or input is registered; the runtime does not infer it from the UI structure. EffectiveBindings overlays scopes, and action handlers are searched inner → outer. See two lookup directions.
Focus
Replacing the top frame's Context with a registered input's path and ID. No frame is pushed. See Flow 1.

Input and editing

Input / InputID
An Input owns text, cursor, mode, and history. A Context refers to it by InputID and never holds a copy. input.go.
Mode
The focused input's editing mode, such as normal, insert, or a visual mode. Without an input, the runtime uses the top frame's state.mode, else normal. Bindings can be restricted to a mode.
Pending vs editor grammar
Runtime.Pending holds a partly typed binding sequence. Editor grammar uses the Input's own state for counts and operators. An unfinished editor command can consume a key before binding resolution; otherwise unhandled binding keys can fall through to the editor. See before binding resolution.

Bindings and operations

Binding / key sequence
A { mode, keys, request } entry. keys may be one key or a sequence such as g g. Ambiguous prefixes wait for a timeout. See the sequence stepper.
Request
What a binding produces: { verb, noun, target, args }, keyed as noun.verb.
Operation / action / Handler
An Operation is a registered noun.verb with parameters and a default Run. A layer action is a layer's own Handler for that key, which wins when found while searching inner → outer. A Handler has signature func(*Runtime, Context, Arguments) (any, error).
Verb / noun
A request's verb is the action (push, pop) and its noun is the target kind (modal). Dispatch looks up the complete noun.verb key in each contextual layer's Actions; it does not filter those layers by their Noun field.

Drawing

View / render / compositor / viewport
Model.View builds the screen: it renders the active page's content through a viewport (scrolling kept in the base frame's state), then draws each modal in Frames[1:] over it using ComposeModal. A renderer produces content; the compositor combines surfaces; a viewport bounds and scrolls content. model.go.

01The shared pipeline

The framework owns state and dispatch. The demo defines its pages, inputs, and bindings. Tab and Ctrl-N follow the same five steps below. The sandbox uses its own Update and View, but shares the runtime's matching and execution.

  1. 1 · Bubble TeaA tea.KeyMsg reaches Update.
  2. 2 · AdapterModel.dispatchKey checks macros, palette, and input grammar.
  3. 3 · RuntimeHandleBinding builds the sequence and matches it.
  4. 4 · ExecuteExecuteAt finds a layer action or the operation's Run.
  5. 5 · StateThe handler changes runtime state (a context, a frame, input text, a page), then View renders.
Framework

Runtime and Model

Owns Context, Frames, Pending, HandleBinding, ExecuteAt, and the built-in modal.push operation.

Demo

NewDemo

Owns the page names, the input IDs directory, notes, and dialog, the input.next handler, and the tab and ctrl+n bindings. The comment at demo.go:12 says the framework requires none of these names.

Context.Path is not Frames

Context says where input goes: an ordered list of layer IDs from app to the innermost layer, plus an optional focused InputID. Frames is the visual and interaction stack: the page frame first, then each open modal, drawn bottom to top. Each frame carries its own Context, so the last frame also decides where keys go. The runtime's current context is the context of the last frame. Full glossary.

Where Model.Update hands off

Model.Update splits ordinary multi-rune key messages into single keys, then calls dispatchKey. The call to HandleBinding comes after the macro, palette, paste, and in-progress input-grammar checks. See which interaction gets each key first.

A key that no binding handles falls through to HandleInputKey, which is the text editor. Both flows below are handled earlier, at HandleBinding.

01aBefore binding resolution

The framework does not send every key straight to your configured bindings. It first checks whether an active interaction needs that key. A register prompt, an open palette, a paste, or an unfinished editor command can take priority over the ordinary binding path.

Two separate decisions The router decides which handler gets the key first. Layer precedence decides which configured binding wins once binding resolution runs. The routing order below is hard-coded in Model.dispatchKey, not assembled from layers.

  1. A macro command may be waiting for a register

    In normal mode, press q to begin recording, then a to choose register a. The second key answers the register prompt. It should not trigger an unrelated binding for a.

    Illustrative state · simplified JS 
    before = { macroPending: "q" }
keypress = "a"
after = { recordingInto: "a" }

    A replay command can also wait for a register. The early macro check handles that pending choice or a recording-stop key. It does not consume every key while recording: ordinary recorded keys continue through dispatch.

    Source: macro recording and early handling.

  2. An open palette takes over routing

    If the palette is active, dispatchKey calls Palette.HandleKey and returns. The key does not continue through the ordinary page-input path.

    This does not disable configured bindings. The palette handler calls Runtime.HandleBinding itself, using the palette's active context, before its navigation and editor handling.

  3. A paste is text, not a series of shortcuts

    On the ordinary page-input path, a paste goes directly to HandleInputKey. Pasting hello should deliver text to the editor, not execute bindings for h, e, and the remaining letters.

    The palette branch comes earlier. This paste bypass describes the ordinary page-input path, not a guarantee about the palette's separate handler.

  4. An unfinished editor command gets first chance to finish

    “Input grammar” means the editor's rules for commands and counts, such as d w and 3 j. Suppose the editor has already accepted d as a delete operator, and the app also has a shortcut for w.

    Illustrative state · simplified JS 
    appBinding = { keys: "w", action: "switch-page" }
editor = { mode: "normal", pending: "d" }
keypress = "w"

// The editor gets first chance:
result = "complete d w: delete a word"
// Not: interrupt the command to switch pages.

    If Input.Pending or Input.Count is set, the input handler gets the key before the configured bindings. Dispatch stops if that handler reports the key handled or returns an error. Otherwise, resolution continues.

    This priority applies to an already-started command. A fresh key still reaches configured bindings before ordinary editor handling. The condition also covers an app-level macro count when no input is focused.

    Source: in-progress grammar and count check.

  5. Now the ordinary path resolves configured bindings

    Runtime.HandleBinding(key.Key) resolves the effective bindings and any pending binding sequence. A handled key stops here. It does not also become editor input.

    If binding resolution does not handle the key, the router checks whether normal-mode Escape should close a modal. Otherwise, it falls back to HandleInputKey.

    Source: binding dispatch and final fallback.

02Two lookup directions

Bindings and handlers resolve in opposite directions. The difference matters when two layers define the same thing.

Bindings

Outer → inner, last write wins

EffectiveBindings walks Context.Path from app inward. For each layer it writes the mode-less bindings into a map keyed by the full key sequence, then the bindings for the current mode. The innermost layer writes last, so it overwrites.

Handlers

Inner → outer, first hit wins

ExecuteAt walks the path from the end back to app and runs the first layer whose Actions map has the key noun.verb. If no layer has one, it runs the operation's registered default Run.

The demo uses this split for selection.inspect. The registry default at demo.go:93-96 reports app. The layers playground, agent, and directory override it at demo.go:97-103.

Note Bindings overlay complete key sequences, not single keys. A binding for g g replaces another binding for g g and leaves g alone (runtime.go:297).

03Flow 1 · Tab moves directory → notes

Starting point. The user is on the Playground page with the directory field focused. The demo registers that page's frame with that context at demo.go:45, and OpenPage installs the frame as Frames (pages.go:50-62).

Illustrative snapshot · simplified JS, not real output 
// BEFORE
Frames: [{
  id: "playground",
  context: {
    path: ["app","playground",
           "agent","directory"],
    inputId: "directory"
  }
}]
Runtime.Pending: ""
// AFTER
Frames: [{
  id: "playground",
  context: {
    path: ["app","playground",
           "agent","notes"],
    inputId: "notes"
  }
}]
Runtime.Pending: ""

  1. The user presses Tab

    Bubble Tea sends a tea.KeyMsg whose String() is "tab". Model.Update passes it to dispatchKey (model.go:81-102).

  2. The adapter lets it through

    No macro is pending, the palette is closed, the key is not a paste, and the directory input has no pending grammar. So the checks at model.go:128-149 do not return, and the call at model.go:150 runs.

  3. The runtime finds an exact match

    Pending is empty, so sequence is "tab". EffectiveBindings includes the playground binding below. It has no mode, so it applies in every mode. Tab is complete with no longer continuation, so the matcher clears pending state and executes immediately.

  4. ExecuteAt chooses the handler

    The request key is input.next. No layer on the path has an Actions["input.next"] entry, so the loop at runtime.go:235-240 falls through to the registered Run. That is the demo's handler.

  5. The demo handler picks the next field

    The handler refuses to run unless the active page is playground and no modal is open. It finds the current InputID in the ordered list, adds delta (default 1), wraps, and calls r.Focus.

  6. The runtime rewrites the top frame's context

    Focus looks up the input's registered path, validates it, and replaces the top frame's Context. No frame is pushed, so Frames keeps its length of 1. Only Context.Path and InputID change.

  7. The view follows the context

    HandleBinding returns handled = true, so the key never reaches the text editor. On the next View, the playground page renders notes as the active field (demo.go:169-190). The path to notes is registered at demo.go:23.

Who did what. The framework matched the key, ran the handler, and moved focus. The demo decided that directory, notes, and paths form a cycle.

04Flow 2 · Ctrl-N opens the draft modal

Starting point. The user is in the notes field, in normal mode. A new input starts in "normal" mode (input.go:37). This matters: the binding below only exists in normal mode.

Illustrative snapshot · simplified JS, not real output 
// BEFORE
Frames: [
  { id: "playground",
    context: {
      path: ["app","playground",
             "agent","notes"],
      inputId: "notes" } }
]
Mode(ctx): "normal"
Runtime.Pending: ""
// AFTER  (frame pushed)
Frames: [
  { id: "playground", ...unchanged },
  { id: "draft",
    context: {
      path: ["app","dialog"],
      inputId: "dialog" } }
]
Runtime.Pending: ""

  1. The user presses Ctrl-N

    The key string is "ctrl+n". The adapter reaches HandleBinding the same way as in flow 1, because notes has no pending grammar.

  2. The binding exists only for normal mode

    The binding lives on the playground layer with mode "normal". EffectiveBindings adds it in the second pass over that layer, because Mode(c) equals "normal". In insert mode the binding would be absent.

    The second line explains why Ctrl-N inside the draft nests a second modal. The dialog layer is not on the notes path, so it does not apply yet.

  3. Exact match, then Execute

    ctrl+n is complete with no longer binding, so it is not deferred. HandleBinding clears pending state and calls Execute with modal.push and arguments id: "draft", input: "dialog".

  4. The handler lookup falls to the registry default

    No demo layer defines an action for modal.push. ExecuteAt validates the arguments, then runs the built-in Run from registerCore. This time the framework supplies the handler too.

  5. Push adds a frame

    The new frame's context comes from the input's registered path. The demo registered dialog with path ["app","dialog"] (demo.go:25). Push rejects a duplicate frame ID, validates the context, appends, and clears Pending.

  6. The view draws the modal over the page

    r.Context() now returns the dialog context, so the next key resolves against ["app","dialog"]. The page frame stays underneath, unchanged. The demo registered the draft modal's title and renderer at demo.go:57-70.

Contrast with flow 1 Tab changed the top frame's Context.Path and left Frames at length 1. Ctrl-N changed Frames to length 2 and left the page frame's context alone. Different structures, same pipeline.

05Flow 3 · A configured g g in the sandbox

This flow does not use NewDemo, Model.Update, or the default demo bindings. The ochazuke keybinding command builds its own keybindingModel around a fresh NewRuntime() (keybinding.go:178-179). Its Update is a separate dispatcher that calls the same Runtime.HandleBinding.

Assumed configuration. The user configured the binding g g with action go-top, either in setup or with --bind 'g g=go-top'. This is a configuration choice for the example. It is not a default.

How the configuration becomes a binding

installBinding normalizes the key string, registers an operation with verb go-top and noun sandbox, and appends a binding to the app layer. The operation's Run only records "ACTION: go-top" in the results ring. It moves nothing.

First g: the prefix is stored

  1. The user presses g

    keybindingModel.Update delegates to handleKey, which appends "g" to history and sets the result to "unmatched". It then calls Runtime.HandleBinding.

  2. No exact match, but a prefix match

    sequence is "g". No binding has exactly those keys, so there is no completed fallback. The longer binding "g g" starts with "g ". The runtime stores the pending prefix and deadline.     Back in Update, m.runtime.Pending != "" is true, so the history row reads pending: g.

Second g: the full sequence matches

  1. The user presses g again

    Pending is "g", so sequence becomes "g" + " " + "g", which is "g g".

  2. Complete match, nothing longer

    "g g" is complete and no longer binding extends it, so it runs immediately: Pending goes back to "" and Execute is called with go-top.sandbox. Any timer scheduled by the first g is now stale and does nothing when it arrives.

  3. The registry default runs

    The app layer has no Actions entry for go-top.sandbox, so ExecuteAt calls the Run that installBinding registered. It writes "ACTION: go-top" into the latest history slot. Pending is empty, so the switch falls to no case, and the row keeps the ACTION text.

Illustrative snapshot · after second g 
runtime.Pending: "g"  →  ""
results[1]: "ACTION: go-top"
history: ["g", "g"]   // newest first in the right-hand column

Timed longest match: when g, g g and g g g are all bound

The walkthrough above binds only g g, so the first g is a pure prefix. If a complete binding is also a prefix of a longer one, the runtime now defers it instead of running it at once. The timeout defaults to 1000ms and is set with --timeout or t in setup.

  • Defer. With g, g g and g g g bound, the first g is complete but ambiguous. It is stored as the fallback and a timer is scheduled. The second g is a valid continuation: it refreshes the timer and g g becomes the fallback. The third g has no longer continuation, so g g g runs immediately.
  • Timeout. The timer arrives as a Bubble Tea message, so the runtime is only mutated inside Update. On timeout the longest completed fallback runs. A pure prefix with no completed fallback clears without running; the sandbox shows sequence timed out. The outcome is written to the last key row; no key is invented.
  • Mismatch with a fallback. After g, the key x forms "g x", which matches nothing. The completed fallback g runs and x is consumed.
  • Mismatch without a fallback. If nothing complete was deferred (for example a pure prefix such as g g alone), the pending state clears and the mismatching key is retried on its own, as before.
  • Escape. Esc cancels all deferred work: pending keys, fallback, and timer. The sandbox shows sequence cancelled. Timer events from a cancelled or superseded wait are stale and do nothing. F2, entering the sandbox, and configuration changes also cancel (CancelPendingBinding).
Current resolver HandleBinding defers ambiguous matches. BindingTimeoutCommand and HandleBindingTimeout deliver and resolve the deadline on the event loop. CancelPendingBinding and finishPendingBinding clear stale state before dispatch. These local sources replace the older immediate-exact-match resolver. Set Runtime.BindingTimeout in embedded applications; the default is 400ms.

06Sequence stepper

This stepper is a small illustration written in JavaScript. It does not run the Go code and has no real clock. It mirrors the timed longest-match rules for three bindings, g → single, g g → double, and g g g → triple. The Advance timeout button stands in for the timer firing; it is an illustration control, not live Go. Without JavaScript, the three flows above carry the same information.

Press g to start. Nothing has happened yet.

  • Press g three times. The first two presses defer (single, then double become the fallback). The third has no longer continuation, so triple runs.
  • Press g, g, then Advance timeout. The fallback double runs.
