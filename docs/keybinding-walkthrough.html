01The shared pipeline

The framework owns state and dispatch. The demo defines its pages, inputs, and bindings. Tab and Ctrl-N follow the same five steps below. The sandbox uses its own Update and View, but shares the runtime's matching and execution.

  1. 1 · Bubble TeaA tea.KeyMsg reaches Update.
  2. 2 · AdapterModel.dispatchKey checks macros, palette, and input grammar.
  3. 3 · RuntimeHandleBinding builds the sequence and matches it.
  4. 4 · ExecuteExecuteAt finds a layer action or the operation's Run.
  5. 5 · StateThe handler changes Frames, then View renders.
Framework

Runtime and Model

Owns Context, Frames, Pending, HandleBinding, ExecuteAt, and the built-in push.modal operation.

Demo

NewDemo

Owns the page names, the input IDs directory, notes, and dialog, the next.input handler, and the tab and ctrl+n bindings. The comment at demo.go:12 says the framework requires none of these names.

Context.Path is not Frames

Context says where input goes: an ordered list of layer IDs from app to the innermost layer, plus an optional focused InputID. Frames says what is stacked on screen: the page frame first, then each open modal. The runtime's current context is the context of the last frame.

Where Model.Update hands off

Model.Update splits multi-rune key messages into single keys, then calls dispatchKey. The call to HandleBinding comes after the macro, palette, paste, and in-progress input-grammar checks.

A key that no binding handles falls through to HandleInputKey, which is the text editor. Both flows below are handled earlier, at HandleBinding.

02Two lookup directions

Bindings and handlers resolve in opposite directions. The difference matters when two layers define the same thing.

Bindings

Outer → inner, last write wins

EffectiveBindings walks Context.Path from app inward. For each layer it writes the mode-less bindings into a map keyed by the full key sequence, then the bindings for the current mode. The innermost layer writes last, so it overwrites.

Handlers

Inner → outer, first hit wins

ExecuteAt walks the path from the end back to app and runs the first layer whose Actions map has the key verb.noun. If no layer has one, it runs the operation's registered default Run.

The demo uses this split for inspect.selection. The registry default at demo.go:93-96 reports app. The layers playground, agent, and directory override it at demo.go:97-103.

Note Bindings overlay complete key sequences, not single keys. A binding for g g replaces another binding for g g and leaves g alone (runtime.go:297).

03Flow 1 · Tab moves directory → notes

Starting point. The user is on the Playground page with the directory field focused. The demo registers that page's frame with that context at demo.go:45, and OpenPage installs the frame as Frames (pages.go:50-62).

Illustrative snapshot · simplified JS, not real output 
// BEFORE
Frames: [{
  id: "playground",
  context: {
    path: ["app","playground",
           "agent","directory"],
    inputId: "directory"
  }
}]
Runtime.Pending: ""
// AFTER
Frames: [{
  id: "playground",
  context: {
    path: ["app","playground",
           "agent","notes"],
    inputId: "notes"
  }
}]
Runtime.Pending: ""

  1. The user presses Tab

    Bubble Tea sends a tea.KeyMsg whose String() is "tab". Model.Update passes it to dispatchKey (model.go:81-102).

  2. The adapter lets it through

    No macro is pending, the palette is closed, the key is not a paste, and the directory input has no pending grammar. So the checks at model.go:128-149 do not return, and the call at model.go:150 runs.

  3. The runtime finds an exact match

    Pending is empty, so sequence is "tab". EffectiveBindings includes the playground binding below. It has no mode, so it applies in every mode. The exact-match loop runs first, clears Pending, and calls Execute.

  4. ExecuteAt chooses the handler

    The request key is next.input. No layer on the path has an Actions["next.input"] entry, so the loop at runtime.go:235-240 falls through to the registered Run. That is the demo's handler.

  5. The demo handler picks the next field

    The handler refuses to run unless the active page is playground and no modal is open. It finds the current InputID in the ordered list, adds delta (default 1), wraps, and calls r.Focus.

  6. The runtime rewrites the top frame's context

    Focus looks up the input's registered path, validates it, and replaces the top frame's Context. No frame is pushed, so Frames keeps its length of 1. Only Context.Path and InputID change.

  7. The view follows the context

    HandleBinding returns handled = true, so the key never reaches the text editor. On the next View, the playground page renders notes as the active field (demo.go:169-190). The path to notes is registered at demo.go:23.

Who did what. The framework matched the key, ran the handler, and moved focus. The demo decided that directory, notes, and paths form a cycle.

04Flow 2 · Ctrl-N opens the draft modal

Starting point. The user is in the notes field, in normal mode. A new input starts in "normal" mode (input.go:37). This matters: the binding below only exists in normal mode.

Illustrative snapshot · simplified JS, not real output 
// BEFORE
Frames: [
  { id: "playground",
    context: {
      path: ["app","playground",
             "agent","notes"],
      inputId: "notes" } }
]
Mode(ctx): "normal"
Runtime.Pending: ""
// AFTER  (frame pushed)
Frames: [
  { id: "playground", ...unchanged },
  { id: "draft",
    context: {
      path: ["app","dialog"],
      inputId: "dialog" } }
]
Runtime.Pending: ""

  1. The user presses Ctrl-N

    The key string is "ctrl+n". The adapter reaches HandleBinding the same way as in flow 1, because notes has no pending grammar.

  2. The binding exists only for normal mode

    The binding lives on the playground layer with mode "normal". EffectiveBindings adds it in the second pass over that layer, because Mode(c) equals "normal". In insert mode the binding would be absent.

    The second line explains why Ctrl-N inside the draft nests a second modal. The dialog layer is not on the notes path, so it does not apply yet.

  3. Exact match, then Execute

    The exact-match loop at runtime.go:333-339 finds ctrl+n, clears Pending, and calls Execute with the request push.modal and arguments id: "draft", input: "dialog".

  4. The handler lookup falls to the registry default

    No demo layer defines an action for push.modal. ExecuteAt validates the arguments, then runs the built-in Run from registerCore. This time the framework supplies the handler too.

  5. Push adds a frame

    The new frame's context comes from the input's registered path. The demo registered dialog with path ["app","dialog"] (demo.go:25). Push rejects a duplicate frame ID, validates the context, appends, and clears Pending.

  6. The view draws the modal over the page

    r.Context() now returns the dialog context, so the next key resolves against ["app","dialog"]. The page frame stays underneath, unchanged. The demo registered the draft modal's title and renderer at demo.go:57-70.

Contrast with flow 1 Tab changed the top frame's Context.Path and left Frames at length 1. Ctrl-N changed Frames to length 2 and left the page frame's context alone. Different structures, same pipeline.

05Flow 3 · A configured g g in the sandbox

This flow does not use NewDemo, Model.Update, or the default demo bindings. The ochazuke keybinding command builds its own keybindingModel around a fresh NewRuntime() (keybinding.go:136-137). Its Update is a separate dispatcher that calls the same Runtime.HandleBinding.

Assumed configuration. The user configured the binding g g with action go-top, either in setup or with --bind 'g g=go-top'. This is a configuration choice for the example. It is not a default.

How the configuration becomes a binding

installBinding normalizes the key string, registers an operation with verb go-top and noun sandbox, and appends a binding to the app layer. The operation's Run only records "ACTION: go-top" in the results ring. It moves nothing.

Illustrative snapshot · simplified JS, not real output

    request: { verb: "go-top", noun: "sandbox" } }
]
runtime.Frames: [{ id: "main", context: { path: ["app"] } }]   // from NewRuntime
runtime.Pending: ""

First g: the prefix is stored

  1. The user presses g

    keybindingModel.Update appends "g" to the history and sets the result to "unmatched". It then calls the runtime (keybinding.go:65-77).

  2. No exact match, but a prefix match

    sequence is "g". No binding has the keys "g", so the first loop finds nothing. The second loop finds "g g", which starts with "g ". The runtime stores Pending = "g" and returns handled = true.

  3. The sandbox reports the pending state

    Back in Update, m.runtime.Pending != "" is true, so the history row reads pending: g.

Illustrative snapshot · after first g 
runtime.Pending: ""  →  "g"

Frames, Context.Path: unchanged

Second g: the full sequence matches

  1. The user presses g again

    Pending is "g", so sequence becomes "g" + " " + "g", which is "g g".

  2. Exact match wins

    The exact loop runs before the prefix loop. It matches, sets Pending back to "", and calls Execute with go-top.sandbox.

  3. The registry default runs

    The app layer has no Actions entry for go-top.sandbox, so ExecuteAt calls the Run that installBinding registered. It writes "ACTION: go-top" into the latest history slot. Pending is empty, so the switch falls to no case, and the row keeps the ACTION text.

Illustrative snapshot · after second g 
runtime.Pending: "g"  →  ""
results[1]: "ACTION: go-top"
history: ["g", "g"]   // newest first in the right-hand column

Mismatch, retry, and Escape

The runtime handles three other cases inside the same function. Each one clears Pending.

  • Mismatch. With Pending = "g", the key x forms "g x". Neither loop matches. The runtime clears Pending and calls itself with "x" alone, so x gets a fresh chance (runtime.go:346-351).
  • Escape. With Pending set, Esc clears it and returns handled = true before any matching (runtime.go:324-327). The sandbox shows sequence cancelled.
  • No timeout. Nothing in HandleBinding or the sandbox starts a timer. Pending stays set until a key resolves it, Esc cancels it, or something else clears it. In the sandbox, F2 clears it when you return to setup (keybinding.go:48-52).
Exact wins If both g and g g were bound, the first g would run the g binding at once, because the exact loop precedes the prefix loop. Pending would never be set, and g g would be unreachable. The runtime never waits to see whether a longer sequence might follow.

06Sequence stepper

This stepper is a small illustration written in JavaScript. It does not run the Go code. It mirrors the rules of HandleBinding for one binding, g g → go-top. Without JavaScript, the three flows above carry the same information.

Press g to start. Nothing has happened yet.

  • Press g twice. The first press stores the prefix. The second matches and runs go-top.
  • Press g, then x. g x fails, Pending clears, and x retries alone.
  • Press g, then Esc. The sequence cancels.
  • Wait as long as you like after the first g. There is no timer.
