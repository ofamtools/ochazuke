04 / One request contract

CLI, socket & MCP

The framework provides a Unix-socket adapter for a running UI and an in-process CLI shell with a stdio MCP adapter. These share runtime operations; they do not all connect to the owner's running UI. The framework does not provide an HTTP transport. Use the action catalog for this demo's operation names and parameter schemas.

Live UI socket

The cmd/ochazuke demo CLI sends one JSON request per Unix-socket connection. Listen delivers a CallMsg to the application's UI loop, which handles it through Runtime.HandleCall and Execute. Running the demo with run --headless suppresses terminal rendering but keeps this same event loop and socket path.

// Simplified JavaScript-shaped request; the wire format is JSON.
{
  verb: "undo",
  noun: "input",
  target: "focused-input",
  args: { steps: 1 }
}

With an application running, query its actual registry or invoke an action:

go run ./cmd/ochazuke operations list
go run ./cmd/ochazuke input undo --json '{"steps":1}'

Request and Response in the Go API catalog describe the wire envelopes; Call, Listen and CallMsg provide transport integration. The socket directory must be private and owned by the current user; the socket file has mode 0600. Connections have ten-second deadlines and a 1 MiB request scanner limit. See live CLI setup for socket selection.

Headless CLI and stdio MCP

Applications using cli.Shell execute requests in their own process through Runtime.HandleCall with CallMsg.Headless set, then settle pending work through the delivery contract. They do not need a live UI socket. The shell's mcp serve runs a stdio MCP server with catalog, describe, run and state tools over that headless runtime. It retains the runtime across calls for history and undo, and does not attach to the owner's screen, selections or modals. Pass explicit targets for operations that need them; UI-dependent operations may be unavailable. The cli and cli/mcp APIs live in their subpackages, outside the root API catalog.

Actor attribution

Actor identifies the request issuer for history and agent policy; it is advisory identity, not authentication. Socket and MCP servers bind identity from their startup context rather than trusting a request's actor or an MCP tool argument. cli.Shell.Actor can supply CLI identity; otherwise the shell reads OCHAZUKE_ACTOR. Shell.NewMCPServer binds an agent identity for the server's lifetime. Socket directory permissions protect local access; actor labels do not establish authenticated user identities.
