Extensibility

Add behavior to your application without changing Ochazuke itself. Go handlers implement the behavior; configuration connects it to operations and keys.

Code or configuration?

The framework is extensible through its operation registry. Your application supplies handlers, and the runtime exposes them through the same command system as built-in operations.

What you want to changeWhat you write
Bindings, arguments, modes, and pages or modals using existing renderersApplication configuration, as demonstrated by examples/full-project
New business logic, integrations, or rendering behaviorGo code registered with the runtime or application renderer registry

Configuration connects existing behavior. It does not execute scripts or load plugins. The JSON configuration loader in full-project is application code built on the framework's registration APIs.

A new action

Your component owns its data and registers operations that act on it. This example belongs inside your application's setup function, where r is an existing *ochazuke.Runtime.

count := 0

r.Register(ochazuke.Operation{
	Verb:        "increment",
	Noun:        "counter",
	Description: "Increase the counter",
	Parameters: map[string]ochazuke.Parameter{
		"by": {Type: "integer"},
	},
	Result: "integer",
	Run: func(
		_ *ochazuke.Runtime,
		_ ochazuke.Context,
		args ochazuke.Arguments,
	) (any, error) {
		count += ochazuke.IntArg(args, "by", 1)
		return count, nil
	},
})

This registers increment.counter in Runtime.Operations. The handler captures the component's state. Ochazuke's core dispatch code does not need a new case for counters.

Registering an action makes it callable. It does not create a UI for its state. Your page renderer reads count to display it.

The handler receives the runtime, the resolved context, and validated arguments. It returns a result or an error. In this example, omitting by increments the counter by one.

Requests and bindings

A key binding, palette selection, or API caller uses the same request shape. These examples use simplified JavaScript-style data to make the structure visible.

{
	verb: "increment",
	noun: "counter",
	args: { by: 5 }
}

A full-project binding can associate that request with a key sequence. This is an example mapping, not a framework default.

{
	layer: "app",
	mode: "normal",
	keys: "g c",
	request: {
		verb: "increment",
		noun: "counter",
		args: { by: 5 }
	}
}

Actual JSON configuration requires quoted property names. The layer field selects where the example application's loader installs the binding; the core Binding lives inside that layer.

Application code can also call the registered operation directly on the runtime's owning event loop:

result, err := r.Execute(ochazuke.Request{
	Verb: "increment",
	Noun: "counter",
	Args: ochazuke.Arguments{"by": 5},
})

Starting from zero, a successful call returns 5 and leaves count equal to 5. The result and the component state are separate from rendering.

Runtime dispatch

Runtime.Execute uses the active context and delegates to ExecuteAt. The runtime looks up the operation by noun.verb and validates its arguments before calling a handler.

After resolving the target and validating the context, ExecuteAt checks Layer.Actions from the deepest active layer toward the application layer. The first matching override handles the request. If no layer overrides it, the runtime calls the operation's registered Run handler.

context = {
	Path: ["app", "project", "editor"],
	InputID: "notes"
};

request = { verb: "save", noun: "workspace" };

handlerLookup = [
	'Layers.editor.Actions["workspace.save"]',
	'Layers.project.Actions["workspace.save"]',
	'Layers.app.Actions["workspace.save"]',
	'Operations["workspace.save"].Run'
];

This lets workspace.save behave differently inside an editor without changing the binding. Layer action overrides and key binding overrides are separate mechanisms. A layer action still needs a registered operation and must accept that operation's declared arguments.

The palette discovers registered operations through the catalog. CLI and socket callers dispatch the same request contract when your application exposes those entry points.

The full-project example

The example application keeps implementation, declarations, and bindings in separate files:

  • actions.go contains handlerRegistry, the application's Go handler map.
  • config/actions.json declares operation names, parameters, and handler names.
  • registerActions in actions.go resolves those names and calls Runtime.Register. Entries with a layer attach an override instead.
  • config/bindings.json connects key sequences to operation requests.

To add new behavior in that application, add a Go handler to handlerRegistry and declare an action that names it. Add a binding if you want a keyboard shortcut. A plain Ochazuke application can register directly, as the counter example does, without adopting this JSON loader.

A working application action

The existing workspace.greet operation follows this registration path. Run it from the repository root:

go run ./examples/full-project workspace greet --json '{"name":"Ada","repeat":2}'

Output:

"Hello, Ada! Hello, Ada!"

Current boundaries

  • New Go handlers require rebuilding the application. Hot-loaded scripts, a plugin loader, and configuration-defined external-command actions are not implemented.
  • Handlers run synchronously on the owning event loop. Slow work must not block that loop. Background work should return results to the loop rather than mutate runtime state from another goroutine.
  • Runtime.Register rejects invalid or duplicate registrations with a panic. Register each operation once; use layer actions for context-specific overrides.

The extension point is the operation contract: a name, an argument schema, and a handler. Your application retains ownership of its domain data and presentation.

Source: runtime.go and examples/full-project/actions.go. The counter and binding snippets are illustrative, not built-in operations or live runtime state.
