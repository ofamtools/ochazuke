Code or configuration?

Start with an existing verb, setting or catalog capability. The runtime exposes operations through keys, palette, CLI, socket and API; each entrance reads the same metadata and execution checks.

Configuration-defined command actions are implemented. Their argv runs directly, without an implicit shell, as off-loop jobs. This does not load arbitrary Go code into the process. The Action contract describes templates, timeouts, labels, output parsing and foreground execution.

A user action

An illustrative actions.json file adds app.hello to the existing app noun:

[
  {
    "noun": "app",
    "verb": "hello",
    "description": "Print a greeting",
    "command": ["printf", "%s\n", "Hello {{name}}"],
    "parameters": {"name": {"type": "string", "required": true}},
    "label": "Greeting for {{name}}"
  }
]

On configuration load, the action becomes an application verb visible to bindings, palette, help and catalogs. Its stdout becomes the job result: JSON when parsable, JSON Lines when each line parses, otherwise text. base is the alternative convention for a CLI accepting NOUN VERB --json ARGS; foreground: true hands a program the terminal instead of capturing output.

Executable commands come only from the user's own action file. Catalogs, socket requests, binding rows and application records cannot supply command definitions. New Go handlers still require rebuilding.

See actions.go, configuration.go and settings_session.go.

A new action

A component or application owns its state. Register an AppHandler for domain behavior; it receives Ctx and returns Done, Failed or Pending. This setup fragment uses an existing *ochazuke.Runtime named r:

count := 0
r.Register(ochazuke.Operation{
    Noun: "counter", Verb: "increment",
    Description: "Increase the counter",
    Parameters: map[string]ochazuke.Parameter{
        "by": {Type: "integer"},
    },
    Result: "integer",
    App: func(ctx ochazuke.Ctx) ochazuke.Result {
        count += ochazuke.IntArg(ctx.Args, "by", 1)
        return ochazuke.Done(count)
    },
})

This registers counter.increment. r.Define("counter").Verb("increment", handler) is the builder form. A low-level Handler instead receives (*Runtime, Context, Arguments) and returns (any, error); use it for synchronous interaction operations and noun action overrides.

Registration does not draw a counter. Use an instance and typed component for addressable UI state, then render it from a page or modal. Instance.Component holds the state, and Parent connects its scope to the focus path. There are no per-component fields to add to Runtime.

See noun.go · Define, Verb, Action, instance.go · Instance and delivery.go · AppHandler, Ctx.

Requests and bindings

The request contract names noun, verb, optional target and arguments. These are real JSON examples, though the counter is illustrative application behavior:

{
  "noun": "counter",
  "verb": "increment",
  "args": {"by": 5}
}

A flat bindings.json array binds that request in the app noun's normal table. It uses the framework's loader, without requiring the full-project example's application loader:

[
  {
    "mode": "normal",
    "noun": "app",
    "keys": "g c",
    "request": {
      "noun": "counter",
      "verb": "increment",
      "args": {"by": 5}
    }
  }
]

The grouped form uses context: "app/normal" and rows with key/action/args. An instance table uses instance instead of noun. Named guards, key patterns and from sources remain data; a row never contains executable handler code. User rows load after application defaults and can override or unbind them.

value, err := r.Execute(ochazuke.Request{
    Noun: "counter", Verb: "increment",
    Args: ochazuke.Arguments{"by": 5},
})

Called on the owning loop with the counter starting at zero, this returns 5. A key and a direct request share operation execution; direct calls do not synthesize key events.

See bindings_file.go, noun.go · Binding and default_bindings.go.

Runtime dispatch

Runtime.Focus is an instance ID. Runtime.Mode is the single mode name plus payload; pending counts, operators and key prefixes live there. Context() derives the path from instance parents. A focus move resets the mode to the destination's declared mode (including pinned modes); page navigation and modal return remember the appropriate base mode.

For keys, DispatchOutcome checks capture rows outer-first and then bubbles through instance and noun tables inner-first. An input chain includes the shared editor fallback table. Editor motions, Readline keys, counts and operator modes are rows in bindings/editor.json, resolved by this same walk. Named guards allow unavailable rows to fall through. Pending modes are exclusive; multi-key prefixes retain a completed request for timeout or mismatch.

Execute uses the current context and delegates to ExecuteAt. Execution canonicalizes action names and aliases, validates arguments, maps a target through TargetInstance, checks applicability and verb checks, handles confirmation, resolves subjects and dispatches an applicable noun action override or the registered handler. Runtime.ResolveTarget can map foreign record IDs to the instances representing them; an unknown target is refused.

// Illustrative data, not an additional Context API:
Instances = {
  notes:   { Noun: "notes-editor", Parent: "project" },
  project: { Noun: "workspace", Parent: "app" }
};
Focus = "notes";
// Derived Context.Path: ["app", "project", "notes"]
// Noun action lookup: notes-editor -> workspace -> app -> default handler

r.Define("notes-editor").Action("workspace.save", handler) installs a context-specific override while that noun is on the instance ancestry. It still needs a registered operation and accepts that operation's schema. Noun action overrides and binding overrides are separate mechanisms.

See resolve.go · DispatchOutcome, runtime.go · ExecuteAt, TargetInstance instance.go · ActionFor and focus.go · OpenModal, Pop.

Props and stores

A noun's PropSpec rows describe typed fields, a read-only key, label/owner/archive roles, references, defaults, secrets and availability guards. Its Store supplies Get, List, Create, Patch, Delete and optional Watch handlers. Store kinds are Collection (keyed records), Singleton (one thing) and Instances (live runtime instances).

The runtime generates supported standard verbs such as get/list/create/set/delete/watch, with patch as an alias of set and further derived verbs where the schema supports them. A prop-shaped get/set/toggle request goes through those same standard verbs. An explicit application verb can replace a generated standard one. A prop and a verb cannot use the same name; key props are read-only, and fallback values affect display only.

Record editors, argument forms, choices, columns and host catalogs reuse that metadata. RecordSpec supports write-on-change fields or a submit form; applications can use shared lists/tables, outlines, timelines, completion, Settings/About and terminal components before adding custom renderers.

Watch uses a store's push events when supplied. Otherwise known change requests, job completions and Runtime.Changed trigger relisting and record-hash comparison. It does not poll for arbitrary outside writes.

See props.go, standard_verbs.go, standard_watch.go and record_editor.go.

Async work belongs to an instance

The handler's synchronous part runs on the loop. Return Pending for I/O or other slow work, capturing the values it needs before leaving the loop. This handler body assumes load and apply are application functions and imports the standard context package:

query := ochazuke.StringArg(ctx.Args, "query", "")
return ochazuke.Pending(func(workCtx context.Context) (any, error) {
    return load(workCtx, query)
}).Replacing("search").Then(func(current ochazuke.Ctx, value any, err error) {
    // Back on the loop, only while this ticket is current.
    apply(current, value, err)
})

A Ticket{Owner, Job, Slot} identifies the job. Empty slot accumulates independent completions; Replacing cancels older work in the owner's slot. ReplacingAt shares a slot across descendants of a specified ancestor while preserving the requesting owner. Closing an owner cancels its jobs; stale completions never run Then.

A custom Instance.Component can implement HandleMessage, PendingCommand and Close. Runtime delivers messages and drains component commands for the adapter. Application code need not add another component list or key switch to Model.

Cancellation can prevent applying obsolete results; it cannot roll back external side effects. Do not read or mutate live Runtime state from workers. See delivery.go and foreground.go.

Events call verbs through hook rows

DeclareEvent publishes a schema and Emit queues a firing. Built-in events are surface.opened, surface.left and app.quitting. Surface events count change verbs and the nouns changed while that surface was open.

[
  {
    "on": "surface.left",
    "where": {"changed": "task"},
    "do": "tasks-git.sync",
    "from": {"changes": "changes"}
  }
]

This row assumes the application registered tasks-git.sync. Each application owns its own hooks.json; app and catalog extension defaults merge before user rows. where matches event fields and from supplies arguments. Hook execution uses registered verbs, with a bounded event chain. Hook writes are excluded from surface change counters; hooks.enabled turns dispatch off.

See events.go, hooks.go and cli/hooks.go.

Catalog hosting and MCP

The cli package publishes CatalogDoc metadata for nouns, verbs, props, pages and sources. MountNouns registers host names and proxy handlers through HostMount. Extension namespaces keep the host and its extensions separate; for example, an extension's doc may become json.doc. Shared catalog page and detail renderers consume the declared data.

Mounting a catalog does not load Go code. The host owns local focus, mode, instances and rendering state; proxy calls reach the extension's records and checks. Guards only the extension understands remain enforced at the extension. A host supplies target resolution/reveal behavior when a foreign record must become a live row instance.

cli.Shell supports headless requests over the same runtime. Shell.NewMCPServer creates a sequential stdio JSON-RPC backend with fixed catalog, describe, run and state tools, plus optional aliases. The backend retains its in-process runtime across calls and does not attach to a running TUI. Family tools use the single mtm MCP gateway for their mounted verbs.

Advisory actor identity

Actor identifies owner, agent or unknown requests for attribution and policy. MCP binds an agent actor once from startup context; tool arguments cannot supply that identity. Ctx.Actor(), request history and nested jobs retain attribution; agent-right rules and verb checks can allow, ask or refuse. Identity is advisory, not authentication. A terminal pane alone does not imply an agent, and returned record/extension text remains data.

See cli/catalog.go, cli/host_mount.go, cli/page.go, cli/mcp_backend.go, cli/mcp and actor.go.

The full-project example

The example's actions.go keeps Go handlers in handlerRegistry. config/actions.json declares names, schemas and handler references. registerActions registers operations first, then installs entries with On as noun action overrides. config/bindings.json supplies key requests.

This example's configuration loader is application code for assembling its demo. Its handler-name declarations are distinct from the framework's per-user actions.json command/alias format. A plain application can use the runtime and noun-builder APIs directly, and use the standard config loader for user customization.

Current boundaries

  • Runtime and live components belong to one event loop. New Go handlers/renderers require rebuilding; external-command user actions do not.
  • Normal duplicate registrations are refused. The builder can install interaction overrides, and an application verb can replace a generated standard verb. Keep each action's schema consistent across overrides.
  • Shared focus/mode and instance ancestry determine routing. Creating a modal does not copy a page or preserve removed modal children indefinitely.
  • Local Unix sockets and stdio MCP are distinct transports. The headless runtime has no owner's live screen or selection; applicability depends on the backend.
  • Actor attribution is advisory. Catalog declarations, event fields and app data do not authenticate callers or authorize arbitrary executable command definitions.
  • Rendering callbacks are Go functions. Catalogs configure supported UI modules, not arbitrary in-process plugins.

For ownership examples and interactive journeys, return to the architecture field guide. The generated Go API covers the root package; subpackage contracts remain in their own source and Go documentation.
