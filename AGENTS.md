# Ochazuke: agent guide

Go application framework on Bubble Tea **v2** (`charm.land/bubbletea/v2` v2.1.0), Lip Gloss v2 (`charm.land/lipgloss/v2` v2.0.6), Bubbles v2 (`charm.land/bubbles/v2` v2.2.1). Single flat package `ochazuke` at the repo root plus `cmd/`, `examples/`, `docs/`.

## Plans and todos

Family plans, todos and the roadmap live in `~/hub/o-plans/` (`README.md` is the index). Read it before planning work; add or update items there. Do not add a TODO.md or docs/plans/ to this repo.

## Compare with Vim first

- A new feature with a Vim or Neovim counterpart (motions, operators, modes, registers, the command line, options, windows and panes, folds, marks, macros, completion) starts from Vim's own behaviour: read its `:help` (in Vim or Neovim, or vimhelp.org and neovim.io/doc/user) and try it in a current Neovim before designing.
- Mirror it where it fits ochazuke's model; where it does not, say why.
- The plan carries a table of each Vim form, its `:help` tag and ochazuke's behaviour (same, similar with the difference, or not applicable with the reason), and the feature's docs (README or `docs/`) get a short "Compared with Vim" note with the same similarities and differences.

## Read in this order

1. This file.
2. `docs/CODEMAP.md`: generated, one entry per source file with declared types, methods, and the sibling files it leans on. Open the two or three files it points at instead of grepping the package.
3. `docs/MIGRATION-PLAN.md` is the completed migration record (all phases done, each with its commit and decisions). Read it for why something is the way it is and for the after-phase-7 items, not for work in progress.
4. README.md only for the section you need. The "API and ownership" section has the file-to-responsibility table and the ownership rules below in long form.

Regenerate the maps after adding, removing, or renaming files:

```sh
make codemap     # writes docs/CODEMAP.md and docs/CHARM-INVENTORY.md
make reference   # writes docs/reference/ (TestReference fails when it is stale)
```

Do not hand-edit either generated file. If a map entry is wrong, fix the code or the generator in `cmd/codemap` or `cmd/charmrefs`.

## Invariants

- `Runtime` is single-owner state. Call it from the Bubble Tea update loop. Other goroutines and processes go through `Call`/`CallMsg`, never concurrent `Execute`.
- Handlers never reach the `Model` to tell the user something: they post through `ctx.Notify`/`ctx.ClearNotice`/`ctx.Info`/`ctx.Error` (or `r.UI()` without a `Ctx`) and the attached `UISink` shows it. There is no `Runtime.Model`. Modal-view registration and appearance stay on the `Model` (setup and UI state, not messages).
- `Runtime` holds no component fields: operation registry, nouns, instances and parent links, three plain interaction fields (`Focus`, `Mode`, `Page`), the modal chain (private; each open modal's `Payload.Return` is the focus it opened over), two instance indexes (`rows`: list row to owning list; `holders`: every instance that is not a list row, in registration order, the only ones `components()` walks, so delivery costs the non-row instances and never the rows; a list row holds no `Component`), pending-sequence state, `BindingTimeout`, `Quit`, the command queue the adapter drains, the jobs list, the action history ring, the query predicate registry and the `ResolveTarget` hook (`TestRuntimeHoldsNoComponentFields` pins the exact field list). Inputs, lists, pages, the picker, the registers and the UI sink are instances whose `Component` holds the typed object; read them with `r.Input(id)`, `r.List(id)`, `r.PageOf(id)`, `r.Registers()`, `r.UI()`, never a map on `Runtime`.
- Components implement the delivery contract (`HandleMessage`, `PendingCommand`, `Close`). Every result carries its owner instance id, a runtime-wide job id and an optional slot (`Ticket`). Staleness is per job, not per owner: jobs accumulate by default (every completion lands, in finish order); `Pending(work).Replacing(slot)` makes a newer job in the slot cancel the older; `ReplacingAt(scope, slot)` scopes the slot to the owner or an ancestor (previews from any row of one list replace each other; the job stays the row's). A job is dropped only when its owner closes or a newer job claims its slot. An application verb whose handler removed its own instance before returning `Pending` (a chooser's pick closes its modal before `Choose` runs) launches the job on the nearest surviving instance of its old ancestry (the focus the modal opened over), so the completion still lands. `Deliver` settles the job and drops a cancelled or orphaned `Completion`, and tolerates a `Then` that removes its own owner (the message is dropped, no panic); `closeInstance` (Pop, `SetItems`, `RemoveInstance`) cancels the owner's jobs and calls `Close`. `jobs.list` lists running jobs and those finished since the last read (retained up to 32); the snapshot's `/jobs` shows running ones. The `Model` drives components from the instance registry; there is no component list on it.
- An operation is `interaction` (default, runs on the loop) or `application` (an `AppHandler func(Ctx) Result` registered through `Define(noun).Verb`). Application work returned as `Pending` runs off the loop as a `tea.Cmd`; the framework never blocks the loop on application I/O, and the completion lands on the owning instance or is dropped if it closed. Palette, `operations.list`, docs and help show the kind.
- Confirmation is a property of a verb (`Operation.Confirm`, set by `.Confirm("…")` or `confirm.set`), not a modal per call site: it opens the `confirm` noun's modal with `Payload{Prompt, Request}` parented at the focus; `y` runs the stored request (`Request.Confirmed`), `n`/`esc` pop, other keys are swallowed; `{{label}}` reads a `label` argument before the target instance's label; `{{noun}}` is always the verb's noun, never the focused or targeted instance's; a request naming its thing by the noun's key argument (`task delete --id t2`) makes `{{id}}`/`{{target}}` that key and `{{label}}` its stored label; a request that addresses no instance of the verb's noun (a CLI call with positional words) reads the request instead of naming `app`: `{{id}}`/`{{target}}`/`{{label}}` the argument of that name, else the first argument in `ParameterOrder` (no arguments: the focus, as before).
- Operation keys are `noun.verb` (`ochazuke.input.undo`, `ochazuke.macro.stop`, `worktree.remove`): `Request.Key`, `Operation.Key`, `Do("noun.verb")` and `Define(noun).Verb(verb)` all agree, and the CLI spelling is the same words with spaces (`bin ochazuke input undo`, or `bin input undo` by the alias). The action table is flat (`action_names.go`): a key is a name looked up whole, so a noun may be dotted and so may a verb (`dirs.base.add` is the verb `base.add` of `dirs`); read a registered key's parts from its `Operation` (`Runtime.Operation`, `CanonicalKey`, `CanonicalRequest`), and use `SplitKey` (last dot) only for a name nothing is registered under, never `strings.Cut(key, ".")`. An action alias (`ActionAlias`: `NounBuilder.Alias`, `AliasOn`, `Renamed`, `Runtime.AliasAction`/`AddActionAlias`, `actions.json` alias rows) is one more name for an action: `canonicalRequest` rewrites a request named by one to its action with `Request.Via` keeping the alias, the handler reads `Ctx.Invoked`/`Runtime.Invoked` (the name and its noun, the subject side), and every listing (catalog, palette, `?` help, CLI, `bindings list`) shows the canonical name with its aliases, never the alias as an entry of its own (UX-RULES R12). Every framework noun is canonical `ochazuke.<noun>` (registered inside `Runtime.Builtin`; `app` itself stays `app` with its verbs, `app.quit` or an application's own `app.state`, which never collide with the framework's `ochazuke.state`; the v0.16.0 spelling `app.<framework noun>` is a deprecated alias for one release, unless shadowed by an `app` verb of that name) with its short name as an alias: input (keys, `Do`, `Request`, binding files, actions.json, the palette, the CLI) accepts either (`CanonicalNoun`/`CanonicalKey`/`Operation`/`Noun`); history, `bindings.list`, `operations.list`, the snapshot and the catalog print canonical; hints, `?` help, the ticker and o-story recordings print `DisplayKey` (the short name while it reaches the noun). Framework code names its nouns canonically (`Do("ochazuke.settings.set")`, `inst.Noun == "ochazuke.list"`) and never indexes `Operations`/`Nouns` with a short name. `Define(alias)` extends the framework noun; `DefineOwn(name)` gives the application the short name and leaves the framework's reachable as `ochazuke.<name>` (never delete framework verbs to make room). A verb `y` on `x` beside a noun `x.y` is refused. A row in the old two-word `verb.noun` spelling is rewritten on load and reported by `ValidateBindings` for one release (keys of three or more words are never swapped); do not write new ones.
- Every keyboard action dispatches a registered operation through one stack walk (`Runtime.Dispatch`): from the focused instance (after its inner level, when it has one: an input's open suggestions, `Instance.inner`, a level that never holds the focus) outward to `app` (the `modal` noun before `app` while a modal is open; the top modal is a boundary, so the walk stops at the modal instance and skips the instances beneath it, then reads `modal` and `app`), then the `editor` noun as the fallback when an input is on the path (for a focused read-only input the editor level comes right after the input and consumes the editor keys that do not run there, `level.owns`) (a list row or page focus ends at `app`, so editor rows neither answer nor appear in `bindings.list` there; counts, registers and macros are `app` rows and still do). At each level the instance's own rows sit above its noun's, and the first row on the key whose action is available (`Runtime.Available`: the verb guard, read with the row's arguments) answers; a key may be bound to several actions in one context, tried in line order, and when none at a level is available the key goes on out (`DispatchOutcome`: handled, unhandled, or consumed by a `NoopAction` row); the mode table is read before the any-mode table; an exact key beats a key class (`digit`, `upper` (before `alpha`), `alpha`, `ctrl+alpha`, `printable`, `paste`, `alpha-q`, `one-of:…`; the `letter` source reads a letter key lowercased without ctrl+/shift+) beats `any`. Key sequences scan the whole stack per key (Vim typeahead): a sequence extending the keys at any level, inner or outer, waits (`DefaultBindingTimeout` 1000ms), with the innermost exact match as the fallback on timeout or mismatch; `Runtime.Bind` and the builder's `Bind` keep a sequence in progress unless a row they add or remove is on it (its mode, and keys equal to, extending or extended by the keys typed so far), which cancels it; otherwise the innermost hit runs; a level answering with a key class ends the scan. A row whose operation's verb guard is false at the focus does not answer: the walk skips it (as `bindings.list` hides it); `ExecuteAt` refuses such a verb only for direct calls. The CLI is a generic `NOUN VERB` adapter over the same registry. Adding a feature means registering an operation and a row, never a key case: no key-name switch statements exist in `editing.go` or `editor.go`.
- Every pending condition is an exclusive mode with a typed `Payload` on `Runtime.Mode`: `count_pending`, `operator_pending`, `g_pending`, `register_pending`, `macro_pending`, `replay_pending`, a key-sequence prefix (`"normal g"`), the `macro_recording` shadow. Exclusive means only that mode's table answers (no any-mode rows); one-shot means the answering key consumes the mode before its request runs unless the request is `mode.enter`, `count.append`, `mode.leave` or `input.cancel`. Rows are `Request`s.
- A binding row is atomic. A row is a `Request` (one registered operation, arguments sourced from the key, the payload, or the acted-on row's `Data` with `FromRow(arg, field)`, source `row:<field>` (dots walk nested fields, a struct read through its JSON encoding) or `row` for the whole value, the innermost instance with `Data` from the focus out to the answering level, a missing field leaving the argument out; `ValidateBindings` checks the source), a mode transition (`Enter`/`Leave`), or `null` (unbind). A `Func` row is not allowed: `Binding` has no field for Go code. Composite behavior is an operation whose handler calls other operations through `Execute` (`macro.record` runs `macro.append` then `key.dispatch`; `terminal.paste {keys}` runs `terminal.send` first), never code that inspects raw key names or mode names. Conditions are the action's availability (a named guard on the verb, `NounBuilder.When`/`SetAvailability`, plus the guards an application adds to any verb, a framework one included, with `AddVerbAvailability`, all of which must hold), not the row's: a row's own `when` is the older form, still honoured, that `bindings check` lists as a debt (`shadow-idle` is one, keeping `q` a stop only in a quiet normal). The only code allowed to compare key names is the key classifier (`printableKey` and friends) and the single key-name-to-text table (`keyTexts`, read through `keyText`/`textKey`), both in `noun.go` (one exception outside resolution: `cli/ptykeys.go`'s `keyCodes` turns key names into the bytes a pty program expects, as an app's daemon `send-keys` mapping does, and plays no part in binding resolution); Escape cancelling a key-sequence prefix is a generated `"<prefix> esc"` → `mode.leave` row (`withPrefixCancels`), not a branch in the resolver. Func rows are forbidden; the test enforces it: `TestBindingRowsAreAtomic` validates every table of the runtime, model, picker and demo (`ValidateBindings`), the full project and the CSV app do the same, and the test parses `resolve.go` to assert it names no key.
- Change modes with `Input.SetMode`. Never assign `Input.Mode` directly.
- Modals keep their own body instance and existing input instances. Closing one restores interaction state (the focus and mode it opened over, from the modal's `Payload.Return`), not a copy of shared data; when that focus was removed, the nearest surviving ancestor, ending at the page.
- Offsets count runes, not grapheme clusters. Rendering accounts for cell width.
- Custom modes are registered names. Unknown modes are not treated as normal or insert.
- Mode resolution: the mode is global, `Runtime.Mode {Name, Payload}`; `mode.set` (`Runtime.SetMode`) writes it, a pending mode is entered on it and leaves back to its base (`Payload.Return`, `BaseMode()`). Instances hold no mode. A focused input is in the global mode (`Input.Mode` is its editing-mode cache, kept equal to the base mode while focused). A focus change that leaves the current focus stop resets the mode to `normal` with an empty payload, or to the pinned mode of the newly focused noun (`prompt` → insert, `terminal` → terminal); moving inside one stop (a grid's cells, a list's rows) keeps it; `Pop` and `page.open` restore the mode they left. Components follow base-mode changes through `ModeObserver` (the grid's shapes). Focus is one field, `Runtime.Focus`; `Context.Path` is derived. There are no layers and no frames: application state lives with the application, scroll offsets on the `Model`.
- Motions are visual: j/k/}/{/tab move across the screen as drawn; only commands (enter, l, a job completion) jump. The walk is the page's recorded drawing order (`Runtime.Placed`), never registration order or a map, and a list spills into its neighbour stop rather than trapping the focus unless it opts out (`NoSpill`). The page scrolls to keep the focused element visible (scrolloff 2, `Page.Scrolloff`; views report their lines through `Runtime.PlacedAt`), and a list that windows itself keeps the same margin around its selected row inside its window (`windowOffset`, the page's scrolloff, same cap and edge relaxation); pgup/pgdn move the surface only; `ctrl+e`/`ctrl+y` (`view.scroll {lines, count}`, `bindings/scroll.json`, `motion_scroll.go`) move the window of the innermost `LineScroller` on the focus path (a list, timeline or markdown document; one held by another scroller defers to it), else the page's overflowing detail, the cursor kept unless it would leave the scrolloff margin. A page's detail (`AddDetail`) scrolls without the focus: `J`/`K` (`detail.scroll`, counts work) are `app` rows, so any inner noun that binds `J`/`K` (the outline's moves) answers first; the item func is asked on every `Window` and every scroll, so a new item starts at the top even when the scroll comes before the next frame, and the same item keeps its offset across refreshes; the footer shows `J/K detail` only while it overflows (a motion row with its own `Hint` shows; a hint that starts with its key and `/` is shown alone). Key rows stay data (`ValidateBindings` is unchanged), and no framework code names an application noun.
- Focus moves only through the runtime: `SetFocus`/`focus.set`, `focus.next`/`focus.previous` (`}` `{` `tab` `shift+tab` stops, `)` `(` regions, on the app noun in normal mode), `Push`/`Pop`, `OpenPage`, `RemoveInstance`, and `RetargetFocus` for a component that recreates its focused child. Focus landing on a list row (any of these, a page's starting focus included) selects that row in its list by id, so the highlight, `List.Selected` and the keys that answer never disagree. Stops are instances of `Focusable` nouns (list, grid, palette, terminal) and every input, minus `Instance.Unfocusable`; jumps walk the top modal (else the page) in drawing order without descending into a stop and land on the stop's remembered child. Drawing order is recorded, never declared: a stop's view (`List.View`, `InputBlock`, `Terminal.ViewBlock`, `grid.View`, an app component calling `Runtime.Placed(id)`) appends it to its page's frame while `Page.Render` runs, and the walk ranks each stop by the first drawn instance in its subtree, so it is the order on screen (a stack top to bottom, a split left before right) and cannot drift from it; before the page's first frame (as in the CLI) the walk is tree order; once a frame drew any stop, a stop it did not draw (a hidden panel) is skipped by jumps and spills until a frame draws it again (a modal's stops never are; its frame is not recorded), so an app need not mark a hidden stop `Unfocusable`. Focus never rests on what the last frame did not draw (R3.13, `keepFocusShown` in `focus.go`, run by `Model.render` after the page and before the footer, then the page is drawn again): when the focus's stop was not placed (a list row counts as drawn when its list is; a stop not placed hides everything beneath it), it moves to the nearest ancestor below the page the frame drew, else the page's first stop in drawing order (`landing`), else the page, through `setFocus` (mode rule, `lastFocus`); never while a modal is open, before the page's first frame, after a frame that placed no stop, or for a focus on no stop. Apps do not move the focus off a panel they stopped drawing. There is no API that sets a stop order. `list.move` (`j`/`k`/`down`/`up`) past an edge of a focused list on a page spills: past the last row the focus moves to the next stop in drawing order (a list on its first row), before the first row to the previous stop (a list on its last row), never wrapping at the page's first or last stop; a count (`3j`, the `steps` parameter) moves that many rows, stops at the list's edge, and spills as one move only when the selection is already on the edge; a list added with `NoSpill()` (a picker-like list that must keep the focus) and any list in a modal clamp instead; `List.Move` (the API) always clamps.
- Focus is never outside the top level: while a modal is open, `Runtime.Focus` is the top modal instance or a descendant (`focusInTopLevel`, asserted in the focus tests). `SetFocus`/`focus.set` refuse a target outside it ("focus is outside the open modal"); internal moves (`RetargetFocus`, `JumpFocus`, `RemoveInstance`, `Pop`'s fallback) clamp to the modal instance; `Push` of a focus outside the body adopts it under the body while it is open (its own parent comes back on `Pop`), and a focus the body sits beneath (`app`) becomes the body. Rows and noun actions beneath a modal therefore never answer inside it: put a modal input's keys on the modal's own instance or noun. A modal opens only from the top level: while one is open, `Push`/`OpenModal` refuse ("a modal is open above this level", first wins, no queue) unless the opener is inside the top modal: the running request's target or focus (`ExecuteAt` records it), a job completion's owner (`Deliver`), else the focus. The refusal is an ordinary error result, so the CLI, the API and history see it. Nesting from the top (prompt → picker) is allowed; a body reopening itself is too; the same kind twice is an error.
- `Runtime.Page` is the current page, an instance of kind `page` under `app`; it is always an ancestor of `BaseFocus()` (the focus beneath any open modal). A page remembers its focus and mode in `Page.Remembered` while another page is open. Pages are ordered by registration (`PageList`), there is no page map.
- List rows are instances of their nouns (`ListItem.Noun`), created and removed by `SetItems`. Never define a noun per row; give the row's noun the verbs and rows, or put an override on the row instance. `ListItem.Data` is an opaque application value `SetItems` copies to the row instance's `Data` (a verb reads `ctx.Instance.Data`); keep a row's foreign id there instead of a side map. Marked rows fan out through `list.apply {verb, args}` as `<row noun>.verb` per row (only the marked rows a filter shows; a verb with a confirm asks once for all of them). `V` on a list, table or tree with marks enters `visual-line`, a selection drawn into the marks (`list_visual.go`); the list follows the mode (`List.ModeChanged`; a modal over it holds it): while it lasts a row's application verb of the row's noun runs through `list.apply` for every selected row (`Runtime.visualApply`, called by `runRow`; the selection holds while the rows' requests are judged and run), and it ends with that verb (`visual.after-action` `keep` keeps it), `esc` or `V`, the marks going back to the ones it found. Code reads a mode's selection shape (`Runtime.SelectionShape`, `ModeSpec.selection`), never its name; a mode may fall back to another mode's rows for nouns with no table of their own (`ModeExtends`, `ModeSpec.extends`; `visual-line` extends `normal`). A filter (`/`, `list_filter.go`) hides rows from drawing and motions but never removes their instances; a list row holds no `Component`. A list or tree added with `NoMarks()` is a read-only view: `list.mark` is guarded off there (guard `list-marks`), so `space` does not answer and no hint offers it.
- Default keys are data, written once: a framework default goes in its area's embedded file (`bindings/<area>.json`, the grouped format of `bindings_file.go`), never in a Go `Bind` chain; the rule tests (`default_bindings_test.go`) check every action, guard and mode it names and that no two rows clash. Go `Bind` is for rows computed at runtime (an instance's rows, a row from a spec). After moving or adding rows, `bindings defaults` shows where each default comes from.
- Readline and Vim rows are the `editor` noun's defaults, from `bindings/editor.json`; an application overrides a key by binding it on any noun or instance on the stack (rows there resolve before the fallback), or in a binding file (same noun+mode+keys+`when` replaces, `"request": null` unbinds the row with the same `when`; the guard is part of a row's identity, so a row without `when` never replaces or unbinds a guarded one, and the user-bindings loader reports such a row as shadowed in a notice; the editor's implicit `input` guard on `input.*` rows, `ImplicitGuard`, is not part of the identity). The `prompt` noun pins insert mode. `bindings.list` lists every key the focus answers to in its mode, pending modes included.
- The palette is an ex-mode command line, not a staged form: one `prompt` input (`__palette/line`, insert pinned) under the `palette` instance, whose text is the command. Words resolve left to right (verb or noun, the complement, then parameters required-first-then-by-name), each a unique prefix; an omitted noun is the nearest instance's noun on the origin's focus path that has the verb, and the request carries no target, so `ExecuteAt` resolves the instance on that path. A parameter's choices are headed by the parameter the next word fills (`paramHeader`: name, type, required or optional, enum count, source or noun, then its description and `next:` the rest; narrowing drops next, then the description, then the facts, never the name). No completion is highlighted until `palette.move` (`ctrl+n`/`ctrl+p`); `palette.run` (enter) appends a highlighted word, else runs the line as typed or names its first missing word. Its keys are rows on the `palette` noun only; requests a line runs are recorded with the source `palette`, and up/down recall them from the history. A rest parameter (`Parameter.Rest`, `settings.apply`'s `line`) takes the line from its first word to the end verbatim (the CLI joins the remaining words); its source is asked with `query` and `cursor`, and `tab` splices its choice in place (`PaletteEntry.Splice`). A bare alias with `Shadows` (`set`) reads by the next word (`ReadBareAlias`, `alias_shadow.go`): a noun with the verb of its name makes the line that noun's verb (`set mode normal`).
- Three selection rules, kept apart. Page lists (`List.View`): no cursor marker at all, rows start at the list's left edge; a list's selected row is the reverse-video highlight alone; a page list without the focus keeps its selected row marked and is drawn faded as a whole (`Styles.Unfocused`, the `dim-unfocused` setting, default 20 percent toward the background, faint in mono), so the focused row is the one highlight at full strength (a tree editing a line is not faded, `List.faded`), while a list in a modal stays plain until focused (`List.marksSelection`); a focused empty list draws `(empty list)` reversed, so a spill into it shows where the focus went. Marked rows take a `* ` gutter, which every row of that list gets while it has a mark. A table (a list with columns) keeps the same rule for its row: its header line is never highlighted and the selected row's highlight spans the whole width; inside it a `CellSelect()` table's current cell (cell mode, `table_cells.go`, opt-in) is reversed and underlined, the header underlines the current column's title, and the unfocused fade keeps both; every other table (a tree's list, help, settings) selects rows and has no current cell. A visual row selection (`V`) is the list's marks, never a highlight of its own. The palette and its completion list are the other rule: nothing is highlighted and no `> ` marker is drawn until `ctrl+n`/`ctrl+p`, and enter without them runs the typed line, never an implicit entry (`TestPaletteEnterRunsUnlessAWordIsHighlighted`). An input's completion list (`completion_list.go`) keeps the palette rule: nothing is highlighted until `ctrl+n`/`ctrl+p`/`down`/`up`, enter takes a suggestion only once one is highlighted (else the key is the input's), tab takes the highlighted one or the first. A chooser (`chooser.go`, the page picker) is the third: it chooses a row, so its top match is highlighted from the first frame and after every edit, enter takes the highlighted row, `ctrl+n`/`ctrl+p` move it clamped (up from no highlight stays), and nothing is highlighted only when nothing matches (enter then creates, or fails). None renders through another. A card timeline (`timeline.go`) is the stated exception to reverse video: its selected card is drawn by its border (see the timeline row), never reversed.
- A modal hides the terminal cursor beneath it, not the highlights: `Model.render` draws the page with `Focus` and `Mode` set to what the outermost modal opened over (`beneath`, restored before returning, no setter runs), and the backdrop is dimmed with `Styles.Backdrop` (the `modal-dim` setting, default 35 percent toward the background plus faint) re-applied after every reset (`dim`), so a grid's cursor cell and selection stay visible; `modal-highlights` `plain` (default `keep`) draws the backdrop without reverse video or underline (`unhighlight`), so no sliver of a cursor bar shows beside a wide modal.
- Hints derive from bindings. The footer, every modal's hint line and the picker's help are `BindingHints`/`ListBindings` output for the focused instance and mode, each row `key noun.verb` (a row with `Hint` reads `key hint`), never a description, ordered from the innermost level outward (the focused instance, its noun, its parents, the page, then `app`, capture rows with their own level); motions (`Operation.Motion`: `list.move`, `focus.*`, `page.next`/`previous`, `surface.scroll`, `input.move`, …; apps mark their own with `NounBuilder.Motion`) and `Hidden` rows (counts, registers, macros, `.`, `g y`, `ctrl+e`/`ctrl+y`, `ctrl+c`, the editor's insert keys, the palette's `ctrl+space`; `help.hints-hidden` shows them) stay off the footer, and of rows running the same request only the innermost key shows; `?` help and `bindings.list` still list everything; descriptions are in `BindingHelp` (`HelpRow{Key, Prefix, Final, Operation, Request, Hint, Description, Noun}`: `Operation` is the `Hint` when the row has one, `Request` always the `noun.verb` it runs, grouped by the answering level's noun, innermost first) and `bindings.list`; there are no hand-written hint strings in the framework, so a hint cannot drift from a row. One chrome: `Model.View` renders through `Layout.Shell`, the same method `Layout.PageBlock` uses; no second set of height or padding constants exists.
- The framework package holds no application pages. The demo is `internal/demo`; tests that need an application build one from the public API.
- One-way module graph: the root module never imports monogatari (`github.com/unixsuperhero/monogatari`, the story library), not even in a test (`go list -deps -test ./...` shows none). Its users are the nested modules `cmd/o-story` (o-story, the demo story app `cmd/o-story/demo`, the stories) and `examples` (the examples and their explore surveys), each with its own `go.mod` requiring ochazuke and monogatari. The `story` and `explore` packages here are frozen and deprecated (o-json still imports `story`); change monogatari instead.
- A terminal is an instance of the `terminal` noun, which pins the `terminal` mode: its `any`/`paste` rows forward everything to the pane, `ctrl+a` (the `terminal-leader` setting, `TerminalLeaderSetting`, declared by `EnsureTerminalLeader` (an app with terminals calls it; `cli.AddCommands` does); its rows are keyed `{terminal-leader}`, a row naming a setting (`binding_settings.go`), so they follow it with no code finding them; `TerminalLeader()` reads it) enters `leader_pending` (`Payload{Shadow, Prefix, Request}` plus the sequence timer; the row's `Hint` makes the footer read `ctrl+a leader: d detaches, ctrl+a sends ctrl+a`), under which `d` detaches, the leader sends itself and a bound key runs. Every pending prefix, the leader and `g g` alike, waits `sequence-timeout` (`SequenceTimeoutSetting`, its default `0s` in the embedded `settings/ochazuke.json`, never a Go constant; `Runtime.BindingTimeout` overrides it in code when positive; `terminal-leader-timeout` is its deprecated name): `0` arms no deadline (`pendingPrefix.forever`), so `BindingTimeoutCommand` schedules no tick and neither `expirePrefix` nor `HandleBindingTimeout` ends it; a focus change, a modal, the pane's removal or a rebind still clears it through `CancelPendingBinding`. A key no row continues a held sequence with (`Payload.Prefix`, whether a prefix mode or a named pending mode) is `sequence-unknown`'s: `pass` runs the stored request (the leader alone) and dispatches the key fresh, `swallow` drops both with a notice. No branch names a mode. `terminal` is a passthrough mode (`DefinePassthrough`): while it is the base mode (`leader_pending` over it included) the walk has no capture pass, so the app's captured `ctrl+c` → `app.quit` stands aside and `ctrl+c` reaches the pane (under the leader it is sent after the leader, by `sequence-unknown` pass); to quit, detach first (`ctrl+a d`, then `ctrl+c`) or bind a key into `leader_pending` to `app.quit`. Frames reach the component only through `Runtime.Deliver` with a current ticket; the stream (a daemon client, or `cli.PtyStream` for a local process) is the application's, never the root package's. `Terminal.Close` releases a stream that implements `TerminalReleaser`, once, so every close path (Pop, `SetItems`, `RemoveInstance`) gives back the lease; detach keeps the pane unless the terminal was added with `CloseOnDetach()`, which removes it; `FocusOnClose(id)` on any instance sends the focus to `id` (when it survives, else the parent or Pop's return) whenever that instance is removed holding the focus, so a detach lands back on the row it was attached from.
- Every chrome or motion rule has a story in `cmd/o-story`; a UI bug is reproduced as a story before it is fixed. A known gap is a story that fails, marked `"skip": "gap: …"`.
- Never bind function keys (F1 to F12) anywhere, including demos, sandboxes, and tests. Use ordinary keys or Ctrl/Alt combinations and keep help text in sync with the real binding.
- This is Bubble Tea **v2**. The v1 idioms are gone: no `tea.KeyMsg` struct (`tea.KeyPressMsg` and `tea.PasteMsg`; a paste reaches `Dispatch` as `MacroKey{Key: "[text]", Paste: true}` and matches only `paste` rows), no `View() string` (`View() tea.View` with `AltScreen` set there, not via program options), no `lipgloss.AdaptiveColor` or renderers (`Appearance.Dark` from `tea.BackgroundColorMsg` feeds `lipgloss.LightDark`), no `github.com/charmbracelet/{bubbletea,lipgloss,bubbles}` imports. Ctrl-Space is `ctrl+space`, not `ctrl+@`. Lip Gloss v2 always emits styles; tests inspecting rendered text use the `mono` theme or `ansi.Strip`.

## Building an application on ochazuke

The module path is `github.com/unixsuperhero/ochazuke`. An application is a separate Go module that imports it; `examples/csv` is the reference consumer (built with one 14-line additive change to the core) and `grid/` shows a component built entirely on the public API. Read those two before writing a new app. The sequence an author follows:

1. **Own your state in your own struct** (domain data, persistence, daemon clients). The runtime holds only interaction state. See `examples/csv/app.go` (`App`, the `Patch` shape that is also the undo record).
2. **Define nouns**: `r.Define("worktree").Verb("remove", app.RemoveWorktree).Confirm("Remove {{label}}?").Mode("normal").Bind("x", Do("worktree.remove"))`. Verbs are application handlers `func(Ctx) Result` returning `Done`, `Failed` or `Pending(work)`; `Pending` runs off the loop and its completion lands on the owning instance. Guards: `.When("selecting")` hides and skips a verb when its guard is false. Parameters with `Enum`/`Source` get pick lists in the palette and CLI help; `Noun: "skill"` does the same from the noun (`skill.list` when it is a read with no required parameter, `Runtime.ChoicesSource`, which the catalog publishes as `source`; else the noun's live instances). `.Rows("noun")` after a list verb declares the noun its result rows belong to (the catalog's `rows`; a noun's `Pin` is the catalog's `pin`). `.Positional("name")` fixes which parameters bare CLI words and palette words fill first. `.Columns(Column{...}, ...)` on a noun declares the table a list of its rows draws (the catalog's `columns`; give the list `Columns(r.Noun(noun).Columns...)` and each row `ListItem.Cells`). `.Quiet()` keeps a bookkeeping verb's jobs (a list reload) off the jobs ticker (the catalog's `quiet`). `.State()` after a verb marks it the state source: one call answers every list's rows as JSON Lines, `{"noun":"skill","id":..,"label":..,"data":{..},"cells":[..]}` per line (`cells` optional, one per column the noun declares), no outer array (return `cli.Lines` of `cli.Row`; the shell prints them a line each), the catalog's top-level `state` (`"NOUN.VERB"`). A host decodes it as it arrives with `cli.NewRowReader` (batches by count or wait; a malformed line is skipped silently, a stream with nothing decodable is `ErrNoRows`) and caches it; an extension without one keeps per-list row sources. See `cli.CatalogDoc`. See `examples/csv/verbs.go`, `bindings.go`.
3. **Build the tree**: `r.AddPage`, `r.AddList(id, Parent(page))`, `r.AddInput`, `r.AddTerminal(id, Parent(page), stream)`, `grid.New(...)`. Rows of a list are instances of their noun (`ListItem.Noun`); the focused row's noun decides what keys mean. Never a noun per row. See `examples/csv/main.go`.
4. **Push data, never pull from the UI**: `list.SetItems(rows)` / `grid.SetData(...)` after every domain change; selection is kept by stable id. Read the rows back with `list.Items()` (a copy, its `Cells` and `Tones` included; `Data` is shared) and `list.Len()`. Handlers receive `ctx.Instance` (id, noun, label, data, payload) and act on your state, then refresh. See `examples/csv/app.go` `Apply`.
5. **Prompts and modals**: `r.OpenModal(kind, Payload{...}, WithInput(in, Kind("prompt")))` for a one-line question; `Confirm` on a verb for yes/no. Keys inside a modal never reach the page beneath it.
6. **Keys are data**: default rows in `Define`, user overrides from a JSON file of rows (`LoadBindings`), `bindings list` prints the effective rows for the focus and mode. No key-name switches in application code either.
7. **Checks**: `go test -race ./...`, a `--smoke` run that renders one frame (see `examples/csv/main.go`), and `ValidateBindings` in a test so every row is atomic.

What the framework will not do for you: persistence, domain validation, daemon protocol clients. Those stay in the application; reuse `matomeru-old/internal/daemon` or `gmtm/internal/tuios` for the TUIOS client rather than writing a fifth.

## Checks

The gate is `make test`: gofmt, `go vet` and `go test` of the root module and of both nested modules (`cmd/o-story`: o-story, the demo app and its stories; `examples`). A bare `go test ./...` at the root runs only the root module, so it skips every story; it fails `TestNestedModulesRunToo` saying so, unless `OCHAZUKE_NESTED_TESTS=1` is set, which `make test` sets.

```sh
make test
OCHAZUKE_NESTED_TESTS=1 go test -race ./...   # the root module under -race (make test ran every module)
go run ./examples/core
go run ./examples/full-project --smoke
```

The two nested modules build through the untracked `go.work` (below), against ochazuke and monogatari at HEAD; `GOWORK=off make test` builds them against the tags their `go.mod` files name. Explorer surveys are not part of `go test` (their tests carry the `explore` build tag): run `make explore` (or `make explore-quick`) when changing `explore/`, the chrome or keys it checks, or before a release if wanted, and `go vet -tags explore ./...`.

## Releasing

Semver tags on `main`; the family bins require the tag. ochazuke requires a tagged oden: release oden first when ochazuke needs an unreleased oden change.

1. Pick the version (`v0.x.y`: minor for API changes, patch for fixes).
2. Add a `## vX.Y.Z (DATE)` section to CHANGELOG.md above o-inventory's dated entries, with the highlights.
3. Run the checks above with `GOWORK=off` (the build a fresh clone gets: `GOWORK=off make test`, which tests the nested modules against the tags they require) and `go mod tidy` (no diff); commit and push.
4. `git tag -a vX.Y.Z -m "..."` on that exact commit, `git push origin vX.Y.Z`, `gh release create vX.Y.Z --notes ...`. Never move or delete a pushed tag; fix forward with the next patch.
5. Check the proxy: `GOPROXY=https://proxy.golang.org GOFLAGS=-mod=mod go list -m github.com/unixsuperhero/ochazuke@vX.Y.Z`.
6. Bump consumers (matomeru, nabe, the o-* bins, mtm-mermaid): `go get github.com/unixsuperhero/ochazuke@vX.Y.Z && go mod tidy`, gate with `GOWORK=off`, commit and push.
7. When the release's stories need a new monogatari (a new story-format field or runner change): bump monogatari to `vX.Y.Z` and tag it (release ochazuke first when monogatari needs an unreleased ochazuke change). Then bump the nested modules: in `cmd/o-story` and `examples`, `GOWORK=off go get github.com/unixsuperhero/ochazuke@vX.Y.Z github.com/unixsuperhero/monogatari@vM && GOWORK=off go mod tidy`, pass `GOWORK=off make test` (every module, against the new tags), commit and push.

Local development uses an untracked `go.work` (`go work init . && go work use ./cmd/o-story ./examples ../monogatari ../oden`), ignored via `.gitignore`, so builds use the sibling checkouts while `GOWORK=off` uses the tags. Never commit a `replace` to a local path or a shared `~/proj/go.work`.

### The Charm SSH stack used by tuios

- `charm.land/ssh`: an SSH **server** library, a fork of gliderlabs/ssh, wrapping `x/crypto/ssh` with a net/http-like API.
