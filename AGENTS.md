# Ochazuke: agent guide

Go application framework on Bubble Tea **v2** (`charm.land/bubbletea/v2` v2.1.0), Lip Gloss v2 (`charm.land/lipgloss/v2` v2.0.6), Bubbles v2 (`charm.land/bubbles/v2` v2.2.1). Single flat package `ochazuke` at the repo root plus `cmd/`, `examples/`, `docs/`.

## Invariants

- `Runtime` is single-owner state. Call it from the Bubble Tea update loop. Other goroutines and processes go through `Call`/`CallMsg`, never concurrent `Execute`.
- `Runtime` holds no component fields: operation registry, nouns, instances and parent links, three plain interaction fields (`Focus`, `Mode`, `Page`), the modal chain (private; each open modal's `Payload.Return` is the focus it opened over), pending-sequence state, `BindingTimeout`, `Quit`, the command queue the adapter drains, the jobs list, the action history ring and the query predicate registry (`TestRuntimeHoldsNoComponentFields` pins the exact field list). Inputs, lists, pages, the picker and the registers are instances whose `Component` holds the typed object; read them with `r.Input(id)`, `r.List(id)`, `r.PageOf(id)`, `r.Registers()`, never a map on `Runtime`.
- Components implement the delivery contract (`HandleMessage`, `PendingCommand`, `Close`). Every result carries its owner instance id, a runtime-wide job id and an optional slot (`Ticket`). Staleness is per job, not per owner: jobs accumulate by default (every completion lands, in finish order); `Pending(work).Replacing(slot)` makes a newer job in the slot cancel the older; `ReplacingAt(scope, slot)` scopes the slot to the owner or an ancestor (previews from any row of one list replace each other; the job stays the row's). A job is dropped only when its owner closes or a newer job claims its slot. `Deliver` settles the job and drops a cancelled or orphaned `Completion`, and tolerates a `Then` that removes its own owner (the message is dropped, no panic); `closeInstance` (Pop, `SetItems`, `RemoveInstance`) cancels the owner's jobs and calls `Close`. `jobs.list` lists running jobs and those finished since the last read (retained up to 32); the snapshot's `/jobs` shows running ones. The `Model` drives components from the instance registry; there is no component list on it.
- An operation is `interaction` (default, runs on the loop) or `application` (an `AppHandler func(Ctx) Result` registered through `Define(noun).Verb`). Application work returned as `Pending` runs off the loop as a `tea.Cmd`; the framework never blocks the loop on application I/O, and the completion lands on the owning instance or is dropped if it closed. Palette, `operations.list`, docs and help show the kind.
- Confirmation is a property of a verb (`Operation.Confirm`, set by `.Confirm("…")` or `confirm.set`), not a modal per call site: it opens the `confirm` noun's modal with `Payload{Prompt, Request}` parented at the focus; `y` runs the stored request (`Request.Confirmed`), `n`/`esc` pop, other keys are swallowed; `{{label}}` reads a `label` argument before the target instance's label.
- Operation keys are `noun.verb` (`input.undo`, `macro.stop`, `key.dispatch`): `Request.Key`, `Operation.Key`, `Do("noun.verb")` and `Define(noun).Verb(verb)` all agree, and the CLI spelling is the same string with a space (`ochazuke input undo`). A row in the old `verb.noun` spelling is rewritten on load and reported by `ValidateBindings` for one release; do not write new ones.
- Every keyboard action dispatches a registered operation through one stack walk (`Runtime.Dispatch`): from the focused instance outward to `app` (the `modal` noun before `app` while a modal is open; the top modal is a boundary, so the walk stops at the modal instance and skips the instances beneath it, then reads `modal` and `app`), then the `editor` noun as the fallback when an input is on the path (a list row or page focus ends at `app`, so editor rows neither answer nor appear in `bindings.list` there; counts, registers and macros are `app` rows and still do). At each level the instance's own rows sit above its noun's; the mode table is read before the any-mode table; an exact key beats a key class (`digit`, `alpha`, `printable`, `paste`, `alpha-q`, `one-of:…`) beats `any`. Key sequences scan the whole stack per key (Vim typeahead): a sequence extending the keys at any level, inner or outer, waits (`DefaultBindingTimeout` 1000ms), with the innermost exact match as the fallback on timeout or mismatch; otherwise the innermost hit runs; a level answering with a key class ends the scan. A row whose operation's verb guard is false at the focus does not answer: the walk skips it (as `bindings.list` hides it); `ExecuteAt` refuses such a verb only for direct calls. The CLI is a generic `NOUN VERB` adapter over the same registry. Adding a feature means registering an operation and a row, never a key case: no key-name switch statements exist in `editing.go` or `editor.go`.
- Every pending condition is an exclusive mode with a typed `Payload` on `Runtime.Mode`: `count_pending`, `operator_pending`, `g_pending`, `register_pending`, `macro_pending`, `replay_pending`, a key-sequence prefix (`"normal g"`), the `macro_recording` shadow. Exclusive means only that mode's table answers (no any-mode rows); one-shot means the answering key consumes the mode before its request runs unless the request is `mode.enter`, `count.append`, `mode.leave` or `input.cancel`. Rows are `Request`s.
- A binding row is atomic. A row is a `Request` (one registered operation, arguments sourced from the key or the payload), a mode transition (`Enter`/`Leave`), or `null` (unbind). A `Func` row is not allowed: `Binding` has no field for Go code. Composite behavior is an operation whose handler calls other operations through `Execute` (`macro.record` runs `macro.append` then `key.dispatch`; `terminal.paste {keys}` runs `terminal.send` first), never code that inspects raw key names or mode names. Conditions are named guards (`shadow-idle` is the one that keeps `q` a stop only in a quiet normal). The only code allowed to compare key names is the key classifier (`printableKey` and friends) and the single key-name-to-text table (`keyTexts`, read through `keyText`/`textKey`), both in `noun.go`; Escape cancelling a key-sequence prefix is a generated `"<prefix> esc"` → `mode.leave` row (`withPrefixCancels`), not a branch in the resolver. Func rows are forbidden; the test enforces it: `TestBindingRowsAreAtomic` validates every table of the runtime, model, picker and demo (`ValidateBindings`), the full project and the CSV app do the same, and the test parses `resolve.go` to assert it names no key.
- Change modes with `Input.SetMode`. Never assign `Input.Mode` directly.
- Modals keep their own body instance and existing input instances. Closing one restores interaction state (the focus and mode it opened over, from the modal's `Payload.Return`), not a copy of shared data; when that focus was removed, the nearest surviving ancestor, ending at the page.
- Offsets count runes, not grapheme clusters. Rendering accounts for cell width.
- Custom modes are registered names. Unknown modes are not treated as normal or insert.
- Mode resolution: the mode is global, `Runtime.Mode {Name, Payload}`; `mode.set` (`Runtime.SetMode`) writes it, a pending mode is entered on it and leaves back to its base (`Payload.Return`, `BaseMode()`). Instances hold no mode. A focused input is in the global mode (`Input.Mode` is its editing-mode cache, kept equal to the base mode while focused). A focus change that leaves the current focus stop resets the mode to `normal` with an empty payload, or to the pinned mode of the newly focused noun (`prompt` → insert, `terminal` → terminal); moving inside one stop (a grid's cells, a list's rows) keeps it; `Pop` and `page.open` restore the mode they left. Components follow base-mode changes through `ModeObserver` (the grid's shapes). Focus is one field, `Runtime.Focus`; `Context.Path` is derived. There are no layers and no frames: application state lives with the application, scroll offsets on the `Model`.
- Motions are visual: j/k/}/{/tab move across the screen as drawn; only commands (enter, l, a job completion) jump. The walk is the page's recorded drawing order (`Runtime.Placed`), never registration order or a map, and a list spills into its neighbour stop rather than trapping the focus unless it opts out (`NoSpill`). The page scrolls to keep the focused element visible (scrolloff 2, `Page.Scrolloff`; views report their lines through `Runtime.PlacedAt`), and a list that windows itself keeps the same margin around its selected row inside its window (`windowOffset`, the page's scrolloff, same cap and edge relaxation); pgup/pgdn move the surface only. Key rows stay data (`ValidateBindings` is unchanged), and no framework code names an application noun.
- Focus moves only through the runtime: `SetFocus`/`focus.set`, `focus.next`/`focus.previous` (`}` `{` `tab` `shift+tab` stops, `)` `(` regions, on the app noun in normal mode), `Push`/`Pop`, `OpenPage`, `RemoveInstance`, and `RetargetFocus` for a component that recreates its focused child. Stops are instances of `Focusable` nouns (list, grid, palette, terminal) and every input, minus `Instance.Unfocusable`; jumps walk the top modal (else the page) in drawing order without descending into a stop and land on the stop's remembered child. Drawing order is recorded, never declared: a stop's view (`List.View`, `InputBlock`, `Terminal.ViewBlock`, `grid.View`, an app component calling `Runtime.Placed(id)`) appends it to its page's frame while `Page.Render` runs, and the walk ranks each stop by the first drawn instance in its subtree, so it is the order on screen (a stack top to bottom, a split left before right) and cannot drift from it; a stop the last frame did not draw (no frame yet, as in the CLI) follows the drawn ones in tree order. There is no API that sets a stop order. `list.move` (`j`/`k`/`down`/`up`) past an edge of a focused list on a page spills: past the last row the focus moves to the next stop in drawing order (a list on its first row), before the first row to the previous stop (a list on its last row), never wrapping at the page's first or last stop; a count (`3j`, the `steps` parameter) moves that many rows, stops at the list's edge, and spills as one move only when the selection is already on the edge; a list added with `NoSpill()` (a picker-like list that must keep the focus) and any list in a modal clamp instead; `List.Move` (the API) always clamps.
- Focus is never outside the top level: while a modal is open, `Runtime.Focus` is the top modal instance or a descendant (`focusInTopLevel`, asserted in the focus tests). `SetFocus`/`focus.set` refuse a target outside it ("focus is outside the open modal"); internal moves (`RetargetFocus`, `JumpFocus`, `RemoveInstance`, `Pop`'s fallback) clamp to the modal instance; `Push` of a focus outside the body adopts it under the body while it is open (its own parent comes back on `Pop`), and a focus the body sits beneath (`app`) becomes the body. Rows and noun actions beneath a modal therefore never answer inside it: put a modal input's keys on the modal's own instance or noun. A modal opens only from the top level: while one is open, `Push`/`OpenModal` refuse ("a modal is open above this level", first wins, no queue) unless the opener is inside the top modal: the running request's target or focus (`ExecuteAt` records it), a job completion's owner (`Deliver`), else the focus. The refusal is an ordinary error result, so the CLI, the API and history see it. Nesting from the top (prompt → picker) is allowed; a body reopening itself is too; the same kind twice is an error.
- `Runtime.Page` is the current page, an instance of kind `page` under `app`; it is always an ancestor of `BaseFocus()` (the focus beneath any open modal). A page remembers its focus and mode in `Page.Remembered` while another page is open. Pages are ordered by registration (`PageList`), there is no page map.
- List rows are instances of their nouns (`ListItem.Noun`), created and removed by `SetItems`. Never define a noun per row; give the row's noun the verbs and rows, or put an override on the row instance. `ListItem.Data` is an opaque application value `SetItems` copies to the row instance's `Data` (a verb reads `ctx.Instance.Data`); keep a row's foreign id there instead of a side map. Marked rows fan out through `list.apply {verb}` as `<row noun>.verb` per row.
- Readline and Vim rows are the `editor` noun's defaults, generated from `editor_bindings.json`; an application overrides a key by binding it on any noun or instance on the stack (rows there resolve before the fallback), or in a binding file (same noun+mode+keys replaces, `"request": null` unbinds). The `prompt` noun pins insert mode. `bindings.list` lists every key the focus answers to in its mode, pending modes included.
- The palette is an ex-mode command line, not a staged form: one `prompt` input (`__palette/line`, insert pinned) under the `palette` instance, whose text is the command. Words resolve left to right (verb or noun, the complement, then parameters required-first-then-by-name), each a unique prefix; an omitted noun is the nearest instance's noun on the origin's focus path that has the verb, and the request carries no target, so `ExecuteAt` resolves the instance on that path. No completion is highlighted until `palette.move` (`ctrl+n`/`ctrl+p`); `palette.run` (enter) appends a highlighted word, else runs the line as typed or names its first missing word. Its keys are rows on the `palette` noun only; requests a line runs are recorded with the source `palette`, and up/down recall them from the history.
- Two selection rules, kept apart. Page lists (`List.View`): no cursor marker at all, rows start at the list's left edge; the focused list's selected row is the reverse-video highlight alone, and an unfocused list draws every row plain (no highlight, no marker), so one row on screen stands out; a focused empty list draws `(empty list)` reversed, so a spill into it shows where the focus went. Marked rows take a `* ` gutter, which every row of that list gets while it has a mark. A table (a list with columns) keeps the same rule: its header line is never highlighted and the selected row's highlight spans the whole width. The palette and its completion list are the other rule: nothing is highlighted and no `> ` marker is drawn until `ctrl+n`/`ctrl+p`, and enter without them runs the typed line, never an implicit entry (`TestPaletteEnterRunsUnlessAWordIsHighlighted`). Neither renders through the other.
- A modal hides the terminal cursor beneath it, not the highlights: `Model.render` draws the page with `Focus` and `Mode` set to what the outermost modal opened over (`beneath`, restored before returning, no setter runs), and the backdrop is dimmed with the muted style re-applied after every reset (`dim`), so a grid's cursor cell and selection stay visible.
- Hints derive from bindings. The footer, every modal's hint line and the picker's help are `BindingHints`/`ListBindings` output for the focused instance and mode, each row `key noun.verb` (a row with `Hint` reads `key hint`), never a description, ordered from the innermost level outward (the focused instance, its noun, its parents, the page, then `app`, capture rows with their own level); motions (`Operation.Motion`: `list.move`, `focus.*`, `page.next`/`previous`, `surface.scroll`, `input.move`, …; apps mark their own with `NounBuilder.Motion`) and `Hidden` rows (counts, registers, macros, `.`, `ctrl+y`, `ctrl+c`) stay off the footer, and of rows running the same request only the innermost key shows; `?` help and `bindings.list` still list everything; descriptions are in `BindingHelp` (`HelpRow{Key, Operation, Description, Noun}`, grouped by the answering level's noun, innermost first) and `bindings.list`; there are no hand-written hint strings in the framework, so a hint cannot drift from a row. One chrome: `Model.View` renders through `Layout.Shell`, the same method `Layout.PageBlock` uses; no second set of height or padding constants exists.
- The framework package holds no application pages. The demo is `examples/demo`; tests that need an application build one from the public API.
- A terminal is an instance of the `terminal` noun, which pins the `terminal` mode: its `any`/`paste` rows forward everything to the pane, `ctrl+a` enters `leader_pending` (`Payload{Shadow, Prefix, Request}` plus the sequence timer; the row's `Hint` makes the footer read `ctrl+a leader: d detaches, ctrl+a sends ctrl+a`), under which `d` detaches, `ctrl+a` sends itself, a bound key runs, an unbound key sends leader and key in one `Send`, and the timeout sends the leader alone. `terminal` is a passthrough mode (`DefinePassthrough`): while it is the base mode (`leader_pending` over it included) the walk has no capture pass, so the app's captured `ctrl+c` → `app.quit` stands aside and `ctrl+c` reaches the pane (under the leader it is sent as `ctrl+a ctrl+c`); to quit, detach first (`ctrl+a d`, then `ctrl+c`) or bind a key into `leader_pending` to `app.quit`. Frames reach the component only through `Runtime.Deliver` with a current ticket; the stream (daemon client) is the application's, never the framework's. `Terminal.Close` releases a stream that implements `TerminalReleaser`, once, so every close path (Pop, `SetItems`, `RemoveInstance`) gives back the lease; detach keeps the pane unless the terminal was added with `CloseOnDetach()`, which removes it; `FocusOnClose(id)` on any instance sends the focus to `id` (when it survives, else the parent or Pop's return) whenever that instance is removed holding the focus, so a detach lands back on the row it was attached from.
- Every chrome or motion rule has a story in `cmd/o-story`; a UI bug is reproduced as a story before it is fixed. A known gap is a story that fails, marked `"skip": "gap: …"`.
- Never bind function keys (F1 to F12) anywhere, including demos, sandboxes, and tests. Use ordinary keys or Ctrl/Alt combinations and keep help text in sync with the real binding.
- This is Bubble Tea **v2**. The v1 idioms are gone: no `tea.KeyMsg` struct (`tea.KeyPressMsg` and `tea.PasteMsg`; a paste reaches `Dispatch` as `MacroKey{Key: "[text]", Paste: true}` and matches only `paste` rows), no `View() string` (`View() tea.View` with `AltScreen` set there, not via program options), no `lipgloss.AdaptiveColor` or renderers (`Appearance.Dark` from `tea.BackgroundColorMsg` feeds `lipgloss.LightDark`), no `github.com/charmbracelet/{bubbletea,lipgloss,bubbles}` imports. Ctrl-Space is `ctrl+space`, not `ctrl+@`. Lip Gloss v2 always emits styles; tests inspecting rendered text use the `mono` theme or `ansi.Strip`.

## Building an application on ochazuke

The module path is `github.com/unixsuperhero/ochazuke`. An application is a separate Go module that imports it; `examples/csv` is the reference consumer (built with one 14-line additive change to the core) and `grid/` shows a component built entirely on the public API. Read those two before writing a new app. The sequence an author follows:

1. **Own your state in your own struct** (domain data, persistence, daemon clients). The runtime holds only interaction state. See `examples/csv/app.go` (`App`, the `Patch` shape that is also the undo record).
2. **Define nouns**: `r.Define("worktree").Verb("remove", app.RemoveWorktree).Confirm("Remove {{label}}?").Mode("normal").Bind("x", Do("worktree.remove"))`. Verbs are application handlers `func(Ctx) Result` returning `Done`, `Failed` or `Pending(work)`; `Pending` runs off the loop and its completion lands on the owning instance. Guards: `.When("selecting")` hides and skips a verb when its guard is false. Parameters with `Enum`/`Source` get pick lists in the palette and CLI help. `.Rows("noun")` after a list verb declares the noun its result rows belong to (the catalog's `rows`; a noun's `Pin` is the catalog's `pin`). `.Positional("name")` fixes which parameters bare CLI words and palette words fill first. `.Columns(Column{...}, ...)` on a noun declares the table a list of its rows draws (the catalog's `columns`; give the list `Columns(r.Noun(noun).Columns...)` and each row `ListItem.Cells`). `.Quiet()` keeps a bookkeeping verb's jobs (a list reload) off the jobs ticker (the catalog's `quiet`). `.State()` after a verb marks it the state source: one call answers every list's rows as JSON Lines, `{"noun":"skill","id":..,"label":..,"data":{..},"cells":[..]}` per line (`cells` optional, one per column the noun declares), no outer array (return `cli.Lines` of `cli.Row`; the shell prints them a line each), the catalog's top-level `state` (`"NOUN.VERB"`). A host decodes it as it arrives with `cli.NewRowReader` (batches by count or wait; a malformed line is skipped silently, a stream with nothing decodable is `ErrNoRows`) and caches it; an extension without one keeps per-list row sources. See `cli.CatalogDoc`. See `examples/csv/verbs.go`, `bindings.go`.
3. **Build the tree**: `r.AddPage`, `r.AddList(id, Parent(page))`, `r.AddInput`, `r.AddTerminal(id, Parent(page), stream)`, `grid.New(...)`. Rows of a list are instances of their noun (`ListItem.Noun`); the focused row's noun decides what keys mean. Never a noun per row. See `examples/csv/main.go`.
4. **Push data, never pull from the UI**: `list.SetItems(rows)` / `grid.SetData(...)` after every domain change; selection is kept by stable id. Read the rows back with `list.Items()` (a copy) and `list.Len()`. Handlers receive `ctx.Instance` (id, noun, label, data, payload) and act on your state, then refresh. See `examples/csv/app.go` `Apply`.
5. **Prompts and modals**: `r.OpenModal(kind, Payload{...}, WithInput(in, Kind("prompt")))` for a one-line question; `Confirm` on a verb for yes/no. Keys inside a modal never reach the page beneath it.
6. **Keys are data**: default rows in `Define`, user overrides from a JSON file of rows (`LoadBindings`), `bindings list` prints the effective rows for the focus and mode. No key-name switches in application code either.
7. **Checks**: `go test -race ./...`, a `--smoke` run that renders one frame (see `examples/csv/main.go`), and `ValidateBindings` in a test so every row is atomic.

What the framework will not do for you: persistence, domain validation, daemon protocol clients. Those stay in the application; reuse `matomeru-old/internal/daemon` or `gmtm/internal/tuios` for the TUIOS client rather than writing a fifth.

## Releasing

Semver tags on `main`; the family bins require the tag. ochazuke requires a tagged oden: release oden first when ochazuke needs an unreleased oden change.

1. Pick the version (`v0.x.y`: minor for API changes, patch for fixes).
2. Add a `## vX.Y.Z (DATE)` section to CHANGELOG.md above o-inventory's dated entries, with the highlights.
3. Run the checks above with `GOWORK=off` (the build a fresh clone gets) and `go mod tidy` (no diff); commit and push.
4. `git tag -a vX.Y.Z -m "..."` on that exact commit, `git push origin vX.Y.Z`, `gh release create vX.Y.Z --notes ...`. Never move or delete a pushed tag; fix forward with the next patch.
5. Check the proxy: `GOPROXY=https://proxy.golang.org GOFLAGS=-mod=mod go list -m github.com/unixsuperhero/ochazuke@vX.Y.Z`.
6. Bump consumers (matomeru, nabe, the o-* bins, mtm-mermaid): `go get github.com/unixsuperhero/ochazuke@vX.Y.Z && go mod tidy`, gate with `GOWORK=off`, commit and push.

Local development uses an untracked `go.work` (`go work init . && go work use ../oden`), ignored via `.gitignore`, so builds use the sibling checkouts while `GOWORK=off` uses the tags. Never commit a `replace` to a local path or a shared `~/proj/go.work`.

### The Charm SSH stack used by tuios

- `charm.land/ssh`: an SSH **server** library, a fork of gliderlabs/ssh, wrapping `x/crypto/ssh` with a net/http-like API. Provides `ssh.Session` (the per-connection handle with PTY, env, and I/O), `ssh.PublicKey`, `ssh.Context`, and `ssh.PublicKeyHandler`. tuios uses it to parse `authorized_keys` and as its connection type in `internal/server/auth.go` and `internal/app/ssh_conn.go`.
- `charm.land/wish/v2`: an SSH **app server** built on that library. `wish.NewServer` takes options (`WithAddress`, `WithHostKeyPath`, `WithPublicKeyAuth`, `WithMiddleware`) and runs a middleware chain per session. `wish/bubbletea` runs a Bubble Tea program for each SSH client and `wish/logging` logs connections. tuios uses it for `tuios ssh` in `internal/server/ssh.go`.
- `charm.land/tone`: CharmTone, Charm's color palette. Every color is a `tone.Key` that satisfies `color.Color`, so it drops straight into Lip Gloss. Named colors such as `Pepper`, `Char`, `BBQ`, `Iron`, `Butter`, `Smoke`, `Squid`; `tone.Keys()` lists them. tuios uses it for its default UI palette and contrast checks in `internal/theme/ui.go`.
